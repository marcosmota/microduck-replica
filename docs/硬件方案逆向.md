# Engenharia reversa da solução de hardware do Microduck

> 🌐 Tradução não oficial para pt-BR do [original](https://github.com/fanhao375/microduck-replica). Em caso de divergência, vale o original. Licença: CC BY-NC-SA 4.0 (texto alterado: traduzido do chinês/inglês).

**Chinês simplificado** · [English](hardware-teardown.en.md)

**Método**: a oficial publicou o runtime em Rust como open source, e um runtime que aciona hardware real precisa ter fixados no código o caminho dos dispositivos,
os endereços I2C, os offsets de registradores, o baud rate e o protocolo. **O código é a especificação**.
Todas as conclusões deste texto vêm do código-fonte, das device trees e dos arquivos de configuração do repositório `pollen-robotics/microduck`.

## 1. Arquitetura geral

> 📍 **Primeiro, o ponto mais fácil de errar**: **a placa do controlador, o HAT e a câmera ficam todos na cabeça** (corpo rígido `jaw_soft` do MJCF, `robot_walk.xml:235` e `:247`); a câmera está a cerca de 13 mm do centro da placa do controlador, sem junta entre elas. A cavidade interna do tronco é praticamente ocupada pelos dois servos de guinada do quadril, e a bateria fica presa externamente atrás e embaixo do corpo.
> Pelo pescoço de três graus de liberdade passam apenas dois feixes de fios: o barramento dos servos e a alimentação `+BATT`.
> Detalhes em [Análise de compras de eletrônica · Onde as placas são instaladas](电控采购清单.md#primeiro-entenda-onde-cada-placa-fica).

```
                    ┌──────────────────────────────┐
                    │   Radxa Zero 3W (RK3566)     │  65 × 30 mm
                    │   Armbian / kernel 6.1.115    │  formato Pi Zero
                    └──┬────────┬─────────┬────────┘
          /dev/ttyS2   │        │ 40-pin  │ MIPI CSI
          1 Mbps UART  │        │         │
        ┌──────────────┘        │         └── câmera IMX219 (girada 90°)
        │                       │
        │              ┌────────▼─────────────────┐
        │              │  Pollen RPI Robot HAT    │  placa própria 65×30mm (open source)
        │              │  i2c3 @ 400kHz           │
        │              │   ├ TLV320AIC3104  0x18  │ codec de áudio
        │              │   ├ BMI088   0x19/0x68   │ soldado mas sem uso
        │              │   └ Stemma J5 → ToF 0x29 │
        │              │  a bateria alimenta via esta placa │
        │              └──────────────────────────┘
        │
   ═════╪═══════════ Barramento Dynamixel (Protocol V2, 1 Mbps) ═══════════
        │
        ├── 15 × Dynamixel XL330    ID: perna esq. 20-24 / pescoço-cabeça-boca 30-34 / perna dir. 10-14
        └── placa imu_to_dxl v2      ID: 200      ← a segunda placa própria
              └ LSM6DSV16X
```

**Ideia central de projeto**: **um único barramento Dynamixel resolve tudo**. O IMU não usa I2C: é feito como escravo
Dynamixel no barramento dos servos e é lido na **mesma transação `sync_read`** dos servos.
A tensão da bateria também dispensa medidor de carga — lê-se diretamente a tensão de alimentação que os servos reportam.

## 3. `imu_to_dxl` v2 — a única placa que você precisa desenhar

**O projeto mais engenhoso, e também o mais fácil de replicar por conta própria.**

| Item | Valor |
|---|---|
| Chip do IMU | **LSM6DSV16X** (ST de 6 eixos, com bloco de fusão de sensores em hardware SFLP) |
| Interface | **Barramento Dynamixel** (não I2C!) |
| ID no barramento | **200** |
| Endereço do registrador | **124** |
| Leitura no loop de controle | 12 bytes |
| Bloco completo de diagnóstico | 20 bytes (inclui ainda aceleração bruta, contador de amostras, flags de estado) |

### Layout do bloco de 12 bytes

| Bytes | Conteúdo |
|---|---|
| `0..6` | gyro x/y/z, contagem bruta `i16` little-endian, faixa **±500 dps**, **17,5 mdps/LSB** |
| `6..12` | Quaternion SFLP x/y/z, **meia precisão IEEE (fp16)**; `w = √(1 − x² − y² − z²)` |

### Por que foi projetado assim

1. **Não ocupa um barramento adicional** — é lido de volta no mesmo `sync_read` dos 15 servos, sem custo extra
2. **O host não precisa executar fusão de postura** — o bloco SFLP do LSM6DSV16X emite diretamente no chip o quaternion de rotação de jogo
   e ainda estima sozinho o bias do giroscópio
3. **Transmite só três componentes de w** — o quaternion unitário economiza um par de bytes, e os 12 bytes cabem exatamente em uma transação

### 📍 Esta placa vai no tronco, não na cabeça — e a orientação é fixa

**Este é o ponto mais fácil de errar**, porque a placa do controlador e o HAT estão na cabeça, e é fácil pensar que as três placas estão na cabeça. Quatro evidências:

**① O código-fonte do runtime oficial diz explicitamente**

A primeira linha de `duck-control/src/imu.rs` é `//! The imu_to_dxl v2 board (LSM6DSV16X), decoded.`,
e as três grandezas que ela emite são todas anotadas no referencial do tronco:

```rust
pub struct ImuData {
    /// Angular velocity in the trunk frame, rad/s.
    pub gyro: [f64; 3],
    /// Projected gravity in the trunk frame, unit vector. Upright is `[0, 0, -1]`.
    pub gravity: [f64; 3],
    /// Orientation, trunk→world, scalar-first `[w, x, y, z]`.
    pub quat: [f64; 4],
}
```

**② A orientação de montagem é uma constante, não é qualquer uma**

```rust
/// The board is mounted so that trunk = `[+raw_z, +raw_y, −raw_x]`, a +90° rotation about Y.
pub const DEFAULT_MOUNT: [f64; 4] = [FRAC_1_SQRT_2, 0.0, FRAC_1_SQRT_2, 0.0];
```

Ou seja, **X do tronco = +Z do chip, Y do tronco = +Y do chip, Z do tronco = −X do chip** (rotação de +90° em torno do eixo Y).
Na decodificação, `rotate(self.mount, gyro_sensor)` converte a leitura do sensor para o referencial do tronco.

**③ No MJCF, os sensores usados pela política estão todos ligados ao tronco**

| Site | Cadeia de bodies | Há sensor vinculado? |
|---|---|---|
| **`imu`** | **`trunk_base`** | ✅ `framequat` / `gyro` / `accelerometer` todos ligados a ele |
| `head_imu` | `trunk_base > neck > neck_pitch > yaw_roll_motion > jaw_soft` | ❌ Nenhum |

`banana_pcb_locker` **aparece uma única vez** no texto inteiro, também em `trunk_base` (`robot_walk.xml:92`).

**④ O IMU da cabeça é o BMI088 do HAT, que o software não usa**

O texto original do comentário na device tree diz "**dormant** BMI088" e "(**unused** but still connected) BMI088"
(`deploy/audio/i2c3-pihat.dts:11,31`), correspondendo ao site `head_imu` da tabela acima, que não tem nenhum sensor vinculado.

#### Por que fisicamente também precisa ficar no tronco

Das 61 dimensões de observação da política, as que vêm do IMU são apenas **velocidade angular** e **gravidade projetada**,
e **ambas dependem apenas da postura do corpo rígido ao qual o IMU está fixado, não de qual ponto desse corpo ele está montado**.

Já a cabeça fica atrás de **três juntas em série**: `neck → neck_pitch → yaw_roll_motion`.
Instalado na cabeça, ele leria a postura da cabeça, separada do tronco por três juntas, e a observação não tem termo de compensação do ângulo do pescoço —
com a simulação ligada ao tronco e o robô real na cabeça, o sim-to-real fica desalinhado diretamente.

→ **A posição dentro do tronco pode ser escolhida livremente, mas a orientação precisa estar definida e conhecida.**
Se a orientação for diferente da oficial, basta passar o seu próprio quaternion a `SflpDecoder::new(mount)`; esse construtor existe justamente para isso.

#### A trava fica na parte traseira do tronco, não na cavidade interna

Aplicando o `pos`/`quat` de cada peça de `trunk_base` em `robot_walk.xml` ao STL correspondente e medindo (referencial do tronco, mm):

| Peça | X | Y | Z | Dimensões |
|---|---|---|---|---|
| **`banana_pcb_locker`** | **−32,3 … −28,5** | −27,0 … +27,0 | +31,5 … +38,1 | 4 × 54 × 7 |
| borda traseira de `right_shell` | **−27,8** | | | |
| bateria `np_f970` | −55,3 … −16,7 | ±10,3 | −39,3 … +31,6 | 39 × 21 × 71 |
| `xl330` ×2 guinada do quadril | −8,5 … +20,5 | ±(7,5…27,5) | −13,0 … +21,0 | 29 × 20 × 34 |
| site `imu` | −21,0 | +0,07 | −14,7 | — |

**Toda a faixa de X da trava cai além da borda traseira da carcaça direita** (−32,3 < −27,8), de 0,7 a 4,5 mm para trás —
é uma barra de pressão transversal colada na **parte de trás da carcaça, sobre o topo da bateria**, **não na cavidade interna do tronco**.
Não encontrá-la na cavidade interna é normal.

> ⚠️ "A trava prende justamente a `imu_to_dxl`" continua sendo uma inferência — o MJCF não tem nenhuma geometria da própria placa.
> A única restrição rígida é: **o IMU precisa estar rigidamente fixado em `trunk_base`**.
>
> ⚠️ O arquivo de malha se chama `np_f970.stl`, mas os 39 × 21 × 71 mm medidos são as dimensões da **NP-F550**,
> a F970 de verdade tem cerca de 60 mm de espessura. Veja [Errata do modelo de bateria na BOM](../BOM.md).

### O que é preciso para fazer esta placa por conta própria

- LSM6DSV16X (ou um ST de 6 eixos com pinagem compatível)
- Um MCU pequeno para atuar como escravo Dynamixel Protocol V2 (STM32G0 / CH32V e similares bastam)
- Transceptor TTL half-duplex (o barramento Dynamixel é half-duplex de um fio)
- Alimentação tirada do barramento

**Esta é a placa que mais vale a pena desenhar por conta própria em todo o projeto**: poucos componentes, lógica clara, protocolo público.

## 4. Pollen RPI Robot HAT — **já open source oficialmente, não precisa desenhar**

> 📌 **Errata (2026-09-03)**: esta seção antes tratava a placa como "não open source, precisa de engenharia reversa". **Isso estava errado.**
> Esta placa tem projeto open source completo em [`pollen-robotics/elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT)
> (**Apache-2.0**): esquemático e PCB em KiCad 9, Gerber, BOM, coordenadas de posicionamento, STEP
> e todos os datasheets dos componentes. Na época só se pesquisou o repositório principal `microduck`, deixando passar os repositórios de hardware com prefixo `elec_` na mesma organização.

**Conclusão: para esta placa basta baixar o Gerber oficial e mandar fabricar; esta seção é mantida como registro de comparação "engenharia reversa vs. peça real".**

### ⚠️ Quatro avisos de leitura obrigatória antes de mandar fabricar

**1. Esta placa não tem circuito de carga nem entrada USB-C.**

O repositório tem uma folha `pwr_supply_charge.kicad_sch`, que facilmente leva a pensar que a placa tem carregamento. **É uma folha órfã** —
o `main.kicad_sch` instancia apenas as quatro subfolhas `audio / dynamixel / power / sensors`, sem incluí-la;
o carimbo da folha ainda traz o nome de outro projeto (`Chromapi's Power Supply & Charge`).

Conferência com a BOM de produção: `CN3302` (CI de carga de lítio), `HY2120` (proteção), conector fêmea USB-C,
chave de alimentação, LED indicador, `AO4435`/`FDS6630A` — **nenhum deles existe**.

Os componentes de alimentação realmente presentes na placa são apenas dois:

| Designador | Componente | Função |
|---|---|---|
| `U10` | **LM5050-1** | OR-ing por diodo ideal ＋ detecção de desligamento (IO_06). ⚠️ Fica no trecho `+5V` **depois** do buck, não é proteção contra polaridade invertida na entrada da bateria, veja a errata da árvore de alimentação abaixo |
| `U9` | **AP63205** | Conversor abaixador (buck) |

> **Conclusão: a bateria precisa ser carregada com um carregador externo.** Conectar o USB-C não carrega o robô.

### Árvore de alimentação do HAT (conferida na página 4/6 do esquemático, `dynamixel.kicad_sch`)

```
Bateria NP-F550 ──► +BATT ──┬──► J13 / J14  Dynamixel-3 (TTL 3P, JST EH 2,5mm)
  2S, 6,6–8,2V              │      via termistor TH1 100R, anotação no esquemático "3A max"
                            │
                            ├──► J3 / J11   Dynamixel-4 (RS-485 4P, JST EH 2,5mm)
                            │      direto em +BATT, acionado pelo U8 SIT3088E
                            │
                            └──► C19 10µF/63V ──► U9 AP63205 + L4 6,8µH ──► Q2 / U10 LM5050-1 ──► +5V
                                                    2A / Fsw 1,1MHz         OR-ing por diodo ideal   │
                                                                            + detecção de desligamento (IO_06) │
                                                                                                     ├─► header de 40 pinos Raspberry Pi J4
                                                                                                     ├─► amplificador de áudio PAM8406D
                                                                                                     └─► U3 XC6206P182 → +1V8 (codec)
```

> O `+3V3` é, ao contrário, fornecido pelo lado do controlador ao HAT pelo header de 40 pinos, não é gerado pelo próprio HAT.
>
> ⚠️ **Errata (2026-09-04)**: este texto antes desenhava o U10 LM5050-1 como **estágio anterior** do `+BATT`, **uma posição errada na cadeia**.
> Ordenando pela coordenada X real de cada símbolo na página Power do esquemático:
> `+BATT(153) → C19(219) → U9 AP63205(302) → L4(392) → Q2(558) → U10 LM5050-1(568) → +5V(635)`
> — **U10 e Q2 estão no trecho `+5V` depois do buck** (em conjunto com o "Switch off detection" do IO_06),
> não são proteção contra polaridade invertida na entrada da bateria. **A conclusão de que "os servos recebem a tensão bruta da bateria `+BATT`" não é afetada.**

**Ponto-chave: os servos recebem `+BATT`, não `+5V`.** A placa tem só um buck (U9) e um indutor (L4);
o trecho de 5 V é para a Raspberry Pi, e 2 A não sustentariam 15 XL330. Esta é a
evidência em nível de esquemático de que o [XL330 opera em sobretensão](执行器选型.md#-a-verdade-sobre-a-tensão-o-xl330-opera-em-sobretensão).

A propósito: o lado de entrada do HAT foi projetado para alta tensão (`C19 10µF/63V`, `C20 100nF/50V`, com o comentário
`Power 24V 5A i.e. 7s/25c, from 21V to 29V`) — porque é um **HAT genérico** que a Pollen fez para
"small/medium size robots", não exclusivo do Microduck.
Assim, a tensão do barramento dos servos depende totalmente da bateria que você conecta; o Microduck conecta uma 2S.

**2. Abrir o projeto KiCad exige outro repositório.**

O repositório do HAT **não tem** `sym-lib-table`, `fp-lib-table` nem nenhum diretório `.pretty`,
mas o esquemático referencia `Library_Pollen`, `LCSC_parts_lib` e `Lib_Pollen`. Eles estão em
[`pollen-robotics/lib_KiCAD`](https://github.com/pollen-robotics/lib_KiCAD)
(`Symbols/Library_Pollen.kicad_sym`, `Footprints/Lib_Pollen.pretty`, `LCSC_parts/`).

Abrir sem instalá-lo resulta em uma tela de símbolos não resolvidos.
**Se você só quer mandar fabricar, não precisa dele** — use diretamente o Gerber em `production/`.

**3. Placa de quatro camadas, 118 posições SMT, é obrigatório usar serviço de SMT.**

As camadas do `kicad_pcb` são `F.Cu / In1.Cu / In2.Cu / B.Cu`. A BOM tem 47 linhas e 123 componentes,
incluindo o **codec em VQFN-32** e o **BMI088 em LGA-16** — soldar à mão é inviável, escolha a montagem SMT ao fazer o pedido.

Há 5 linhas DNP (não montadas): `C25`, `R10/R11`, `R16/R17/R41`, `R36/R37` e **`U4`**.

**4. `U4 = CAT24C32` não montado → esta não é um HAT autoidentificável.**

A posição da EEPROM está vazia, então ela não segue o fluxo de detecção automática da `hat-plus-specification`,
e o sistema não reconhece a placa automaticamente. O overlay da device tree precisa ser configurado manualmente.

### Complemento: o lado Dynamixel é, na verdade, de dois padrões

| Designador | Interface | Descrição |
|---|---|---|
| `J13 / J14` | **TTL 3P** (JST EH 2,5mm) | Os XL330 do Microduck usam este |
| `J3 / J11` | **RS-485 4P** (JST EH 2,5mm) | Acionados por `U8 = SIT3088E` |
| `TH1` | Termistor 100R | Proteção contra sobrecorrente |

Ou seja, esta placa **pode acionar tanto Dynamixel TTL quanto 485, e também servos Feetech** (basta trocar o cabo).

### Complemento: não é uma placa exclusiva do Microduck

É um "HAT genérico para robôs pequenos/médios", com três usuários conhecidos:

- **Microduck** (este projeto)
- **Grabette / Casquette** da própria Pollen (rodando em um Pi 4)
- **[`Rhoban/microban`](https://github.com/Rhoban/microban)** de terceiros — robô bípede com 19×XL330 + Pi Zero 2W + 2×18650,
  com **BOM + montagem + guia de impressão completos e públicos** (cerca de $567 o robô completo), vale comparar na hora de comprar

> A descrição desta placa na BOM do `Rhoban/microban` vale ser lembrada:
> *"Ao contrário dos outros componentes, o RPI Robot Hat não é um item pronto: é uma placa open source, e você precisa mandá-la fabricar por conta própria."*
> — **open source ≠ dá para comprar**, ainda é preciso mandar fabricar.

### Componentes na placa

| Componente | Endereço I2C | Descrição |
|---|---|---|
| **TLV320AIC3104** | `0x18` | Codec de áudio da TI, dados I2S + controle I2C |
| **BMI088** | `0x19` / `0x68` | **Foi de fato soldado mas o software não usa** (BOM `U11`; texto original do comentário "dormant", "unused but still connected"). Quando se diz por aí que o Microduck "tem dois IMUs", é a este que se referem |
| **ToF** | `0x29` ou `0x52` | Não está na placa, conectado externamente via **Stemma/Qwiic J5**. O firmware **suporta tanto o VL53L5CX quanto o VL53L8CX**, identificando-os automaticamente pelo revision ID |

- Barramento I2C: **pino 3 / pino 5** do header de 40 pinos (`GPIO1_A0` = SDA, `GPIO1_A1` = SCL)
- Taxa do barramento **400 kHz** (limitada pelo codec e pelo BMI088; o VL53L5CX poderia rodar a 1 MHz)
- Pull-up: **um par de 10k, R12/R13**
- Clock de áudio: MCLK **12 MHz** de cristal fixo, sysclk I2S **12,288 MHz** (256 × 48kHz)
- **A alimentação interna do robô passa por esta placa** (bateria → HAT → controlador)

### ⚠️ Uma armadilha que eles mesmos encontraram (muito clara nos comentários)

O controlador `i2c3` do RK3566, na DTB original, roda no **pinmux M1** (`GPIO3_B5/B6`, perto da porta USB-C),
atendendo o **controlador USB-C PD FUSB302**. Já os pinos 3/5 que o HAT precisa usar são justamente o **pinmux M0** do `i2c3`.

O overlay deles remapeia o controlador para o M0 e desativa o nó fusb302. Consequências:

- **Perde-se a negociação USB-C PD**
- Porém o FUSB302, ao ligar, apresenta por padrão Rd nas duas linhas CC (`SWITCHES0 = PDWN1|PDWN2`),
  então carregadores USB-C (PD ou comuns) **continuam fornecendo 5V** — a placa só precisa de 5V
- A alimentação interna do robô vem da bateria via HAT, sem relação com isso
- A gravação via maskrom é código da ROM, e não é afetada

> As primeiras versões usavam **I2C bit-bang** (`i2c-gpio-pihat`), com alto uso de CPU.
> Só depois de passar para I2C em hardware o **fluxo de ToF a 15 Hz** se tornou viável.
> Os dois modos são mutuamente exclusivos, e o `install.sh` seleciona via `MICRODUCK_I2C_MODE=hw|bitbang`.

### Nó de dispositivo estável

`/dev/i2c-3` é vinculado por regra udev a **`/dev/i2c-pihat`**, e o código consumidor não precisa mudar nos dois modos.

## 5B. Solução de comunicação (confirmada item a item)

### Barramento principal: UART TTL half-duplex de um fio — **não é RS232 nem RS485**

| Item | Valor | Base |
|---|---|---|
| Camada elétrica | **TTL half-duplex de 3 fios** (linha de dados + VDD + GND) | Especificação do produto XL330: JST de 3 pinos, TTL |
| Nível lógico | **3,3 V** | Nível de IO do RK3566 |
| Protocolo | **Dynamixel Protocol V2** | `.with_protocol_v2()` |
| Taxa | **1 Mbps** | `BAUD_RATE = 1_000_000`, registrador EEPROM `baud_rate = 3` |
| Porta | `/dev/ttyS2` = **UART2 do RK3566, pinmux M0** | `robotd.toml`, overlay `uart2-m0` |
| Dispositivos conectados | **16**: 15 servos + 1 placa de IMU | `ids = [200, 20..24, 30..34, 10..14]` |
| Transação única | Um `sync_read` cobre os 16 dispositivos, registradores **124–136** | `bus.rs` |

> ❗ **Não é RS485**. RS485 é diferencial de dois fios, usado nas séries XM/XH do Dynamixel (4 pinos).
> O XL330 é **TTL half-duplex de um fio** (3 pinos). Buscando `rs485|rs232|half-duplex|direction pin` em todo o repositório,
> **zero ocorrências** — o código não tem GPIO de controle de direção, o que indica que **a troca de direção é feita por um circuito de direção automática em hardware**,
> e esse circuito está na placa HAT.

### ⚠️ Armadilha do Armbian: a UART2 vem por padrão com um console de login

> Texto original de `robotd-design.md` §: o Armbian roda por padrão `serial-getty@ttyS2` na UART2,
> e o `agetty` ocupa a porta serial. É preciso `systemctl mask serial-getty@ttyS2`.
> A oficial descobriu, com `fuser -v /dev/ttyS2`, que era o `agetty`.

### Comparação dos protocolos Feetech STS/SCS

Muita gente pergunta: **ao trocar por servos Feetech, o esquema de "fazer o IMU o 16º dispositivo do barramento" continua valendo?**

**Continua.** O Feetech STS/SCS tem sua própria instrução de leitura em lote `SYNC READ` (`0x82`), com uso igual ao do Dynamixel.
A diferença está apenas em **como as respostas voltam**.

| | Dynamixel V2 (XL330) | Feetech STS/SCS |
|---|---|---|
| Camada física | TTL half-duplex de um fio, 3 fios, 1 Mbps | **Totalmente idêntica** |
| Conector | JST EH 2,5 mm | 5264, também de 2,5 mm (⚠️ mesmo passo, recomenda-se confirmar com a peça real os detalhes da trava do invólucro) |
| Cabeçalho do pacote | `FF FF FD 00` | `FF FF` |
| Verificação | CRC-16 | `~sum` (soma invertida) |
| Leitura em lote | `sync read` (**o que a oficial realmente usa**)<br>Há também `fast sync read` 0x8A, mas **não é usado** | **`sync read` 0x82** |
| Modo de resposta | **Um pacote independente** por dispositivo | **Um pacote independente** por dispositivo |
| Viradas de barramento / ciclo | 17 ⚠️ | 17 ⚠️ |
| Faixa de ID | 0–252 | 0–253 (registrador 5) |
| Configuração do baud rate | Registrador `baud_rate = 3` | Registrador 6, `0 = 1M` |

**Evidência**: `scservo_sdk/group_sync_read.py` — `syncReadTx()` envia um pacote de instrução,
`syncReadRx()` recebe um trecho de buffer, e `readRx()` o fatia casando o cabeçalho `[0xFF, 0xFF, scs_id]` um a um:

```python
result, rxpacket = self.ph.syncReadRx(self.data_length, len(self.data_dict.keys()))
while (rx_index + 6 + data_length) <= rx_length:
    if (headpacket[2] == 0xFF) and (headpacket[1] == 0xFF) and headpacket[0] == scs_id:
        break
```

> ⚠️ **"17 vezes" é uma inferência de protocolo (1 instrução ＋ 16 dispositivos respondendo um pacote cada), não uma medição.**
> A conversão para milissegundos depende da velocidade de comutação do buffer tri-state, do intervalo entre pacotes e do comprimento real dos registradores lidos —
> ao receber o hardware, meça com a FE-URT-1.

#### Correção importante: a oficial **não** usa `fast sync read`

O `fast sync read` (`0x8A`) do Protocol V2 de fato consegue concatenar todas as respostas em um único pacote e reduzir as viradas de barramento a 2.
**Mas o runtime do Microduck não o usa** — a busca por `fast_sync_read` / `0x8A` em todo o repositório dá **zero ocorrências**,
e `duck-control/src/bus.rs:236` chama o `sync_read_raw_data` comum:

```rust
.sync_read_raw_data(&self.ids, READ_ADDR, READ_LEN)
.map_err(|e| IoError::Bus(format!("combined imu+motor sync_read: {e}")))?;
```

Isso também é coerente com a frase de `model.rs:84-86`, "500 µs **per device** × 16 devices ＝ 8 ms" —
**se as respostas fossem concatenadas em um pacote, o atraso de virada por dispositivo não seria multiplicado por 16.**

**Portanto o mecanismo de resposta é o mesmo nos dois lados**: um pacote de instrução sai, e cada dispositivo responde com um pacote de status independente.
A Feetech não "carece de leitura em lote", e o Dynamixel também não está usando a variante mais rápida.
As únicas diferenças reais que restam são duas: o **formato do pacote** e o valor padrão de fábrica abaixo.

#### ⚠️ Uma descoberta contraintuitiva: no atraso de fábrica, a Feetech leva vantagem

Posição `7 (0x07)` da tabela de memória do STS, **Return Delay Time**: **padrão 0**, com a observação **"Not functional on STS"**.

Já o XL330 sai de fábrica com `250`, ou seja, **500 µs/dispositivo** — texto original de `duck-control/src/model.rs:84-86`:

> `return_delay_time` … the XL330 ships at 250, which is 500 µs of turnaround **per device**.
> Across **16 devices** that is **8 ms per tick — 40% of a 20 ms budget**

A oficial precisa escrever 0 neste registrador para eliminá-lo. **A Feetech naturalmente não tem esse custo**, e o custo extra de virada que ela tem é em grande parte compensado por isso.

#### Outro registrador a ajustar no lado Feetech

Posição `8 (0x08)` da tabela de memória do STS, **Response Level**, padrão **1** (todos os comandos respondem).
Ao mudar para **0**, apenas read e ping devolvem pacote, e as instruções de escrita comuns deixam de ocupar tempo do barramento —
é o mesmo tipo de ação que a oficial faz ao escrever `return_delay_time = 0` no XL330.

> **Os valores padrão de fábrica são para cenários genéricos; um loop de controle de alta frequência precisa ser ajustado por você.**

## 5C. Por que é preciso um SoC Linux, e não um STM32 / ESP32

O controlador precisa fazer tudo isto ao mesmo tempo:

| Tarefa | Carga |
|---|---|
| ONNX Runtime executando a política | `obs[1,61] → act[1,14]` @ **50 Hz** |
| Streaming de vídeo WebRTC | 720p30 H.264, **codificação por hardware Rockchip MPP** |
| Detecção de objetos na NPU RKNN | `duck_detect.rknn`, 2 Hz (**limite térmico**, a plena velocidade chega a 95°C) |
| Pipeline GStreamer + controle de congestionamento | `rtpgccbwe` ocupa 7,6% de um núcleo |
| Controle Bluetooth + app de celular + WiFi | Pilha de protocolos BlueZ |
| Atualização / reversão de firmware assinado | `updaterd` |

**Um MCU não consegue fazer isso** — só WebRTC + codificação H.264 em hardware + inferência ONNX já exigem Linux + codificador de hardware + NPU.

Daí a escolha: **RK3566 quad-core Cortex-A55 + Mali-G52 + NPU, rodando Armbian**.

> 📌 Mas note: **na fase de protótipo usou-se a Raspberry Pi Zero 2W**.
> Texto original do comentário em `robotd.toml`: o loop de controle de 50 Hz *"is inherited from the prototype, where it was
> chosen on a Raspberry Pi Zero 2W. It has never been re-derived on the Radxa."*
> O Open Duck Mini v2 ainda usa a Raspberry Pi Zero 2W — porque não faz visão nem WebRTC.

### E que MCU há na placa `imu_to_dxl`?

**Não está no repositório** — é o firmware da própria placa, que não faz parte deste repositório open source.
Mas dá para deduzir os requisitos a partir do que ela precisa fazer:

- Atuar como **escravo Dynamixel Protocol V2** (responder ao `sync_read`, ID 200, registrador 124)
- Ler o **LSM6DSV16X** (SPI ou I2C)
- **UART de 1 Mbps** + comutação de direção half-duplex
- Empacotar o quaternion SFLP em fp16

**STM32G0 / STM32G4 / CH32V203 / ESP32 servem todos.** Aqui há liberdade total de escolha —
desde que se comporte como um escravo Dynamixel no barramento, o controlador não se importa com o chip por dentro.

> Texto original do comentário: *"There is no fuel gauge and no ADC. The only measurement available is

## 7B. NPU e inferência de visão embarcada

> Esta seção foi organizada a partir de `docs/project/npu-bringup.md` e `duck-detect/` do upstream.
> É, até agora, o único material que descreve de forma concreta "o que a NPU do RK3566 realmente consegue fazer".

### Especificações da NPU

| Item | Valor | Origem |
|---|---|---|
| Poder de processamento | **0,8 TOPS, INT8, núcleo único** | Abertura de `npu-bringup.md` |
| Nó da device tree | `npu@fde40000` | `status = "disabled"` de fábrica no Armbian |
| Runtime | Runtime do rknn-toolkit2 `librknnrt.so` | Driver 0.9.8 / runtime 2.3.2 (medido) |

### ⚠️ Duas restrições rígidas que podem travar a réplica

**1. O driver só existe no kernel do fabricante, o mainline não tem.**

> Original: *"The driver is the gate: it is part of the vendor kernel, mainline has none,
> and nothing in userspace can work around its absence."*

Isto é muito mais grave do que "a NPU vem desligada por padrão". Em distribuições com kernel mainline (a maioria das imagens oficiais Debian/Ubuntu),
**simplesmente não há NPU, e não há solução em espaço de usuário**. Na réplica, a imagem do sistema não pode ser trocada à vontade.

**2. O Armbian mantém o nó da NPU desligado em todas as Radxa Zero 3.**

Ou seja, uma placa "de fábrica" tem: hardware, kernel, driver, **mas não tem NPU**.

```bash
# Abordagem upstream: roda automaticamente no preinstall hook do robotctl update, falha não é fatal
sudo sh /opt/robot/daemon/current/scripts/setup-npu.sh
# Escreve o overlay → é obrigatório reiniciar → confirmar:
dmesg | grep rknpu
```

O script a executar é **o que vem no pacote de release**, não o `/usr/local/sbin/robot-setup-npu` —
o arquivo-fonte do overlay fica junto do script, e a cópia isolada, na primeira execução, não tem nada ao lado.

### Detector de patos

O modelo é treinado em outro repositório, `pollen-robotics/duck_detector`, e ao chegar aqui já é um `.rknn` quantizado.

> ⚠️ **Esse repositório não é público** (2026-09-04, medido: 404). A documentação oficial o cita, mas o código de treinamento não está acessível externamente,
> só se obtém o `.rknn` pronto. Para treinar por conta própria seria preciso montar um fluxo de treinamento YOLO do zero.

| Item | Valor |
|---|---|
| Rede | `yolo11n` @ **320×320** |
| Classes | **1 classe** (apenas patos) |
| Conjunto de treinamento | **150 quadros em 3 sessions** |
| mAP50 | **0,976** (na session separada para teste) |
| Tamanho após quantização INT8 | **3,9 MB** |
| Perda por quantização | Medido em desktop: 2/2 detectados, sobreposição de caixa de 95% (comparado ao modelo float) |

> Chegar a 0,976 com 150 quadros — uma única classe, alvo fixo, cenário restrito; esta ordem de grandeza de dados
> é uma boa notícia para quem replica.

### Desempenho medido (Radxa Zero 3, limitado a 2 Hz, 30 quadros × 3 rodadas)

| Item | Medido | Descrição |
|---|---|---|
| Latência p50 / p95 | **25,7 ms / 58,4 ms** | Inferência + decodificação, sem decodificação JPEG |
| CPU por quadro | 20,7 ms | **Atenção: este não é o custo da NPU**, veja abaixo |
| Temperatura do SoC | **63 °C** | Ao final da execução limitada |

**Esse número de CPU se interpreta mal com facilidade.** A coluna de latência soma `infer` + `decode`;
a coluna de CPU é a CPU do processo do loop inteiro dividida pelo número de quadros, portanto **inclui também o `letterbox_rgb`** —
uma reamostragem de 1280×720 → 320×320, executada na CPU e totalmente fora da coluna de latência.
Quanto ao restante, se é espera ocupada do `rknn_run` (contando a espera da NPU como CPU), o próprio upstream ainda não mediu direito.

> A 2 Hz, de qualquer forma, é apenas **4% de um núcleo**. Mas, antes de citar o "custo da percepção", é preciso medir esses dois separadamente.

Quanto ao porquê de 2 Hz, veja [§8 Dois detalhes de engenharia que valem copiar](#dois-detalhes-de-engenharia-que-valem-copiar) —
é um **limite térmico, não uma preferência**; a plena velocidade chega a 95 °C.

### Três decisões de engenharia que valem copiar

**1. `dlopen` em vez de linkar.** O `librknnrt.so` é um blob do fabricante, não está em nenhuma fonte Debian;
se for linkado, não é possível fazer cross-compile no CI. O custo é escrever mais um `duck-detect/src/rknn.rs`,
e o benefício é que `cargo board --bins` continua rodando no notebook. O `robotd` carrega o ONNX Runtime pelo mesmo método.

**2. Deixar o runtime fazer a desquantização.** O tensor de saída do modelo quantizado é int8 + scale + zero point.
O `rknn_outputs_get` pode convertê-lo diretamente para float, e o upstream escolheu deixá-lo converter —
o outro caminho é levar o scale para o decodificador, e **um dia ele calcularia errado silenciosamente**.

**3. A ordem de diagnóstico é "roda? → ainda reconhece? → quanto custa?".**
O `duck-bench` reporta exatamente nessa ordem. Um modelo que roda mas não detecta nada
parece idêntico a um normal.

> ⚠️ **A pontuação de um modelo quantizado está em outra escala.** O 0,5 do modelo float não é o 0,5 deste modelo.
> Se não detectar nada, primeiro ajuste o `--threshold` para **0,2** antes de suspeitar que a conversão quebrou.

### O que ainda falta

**Nada no robô consegue obter um quadro de imagem.** O `mediad` tem um ramo tee de NV12 bruto que existe para isso,
mas **nenhum IPC o expõe** — é por isso que, para coletar um conjunto de dados, é preciso antes parar o `mediad`
para conseguir pegar a câmera.

O upstream dá dois caminhos (não excludentes): um é adicionar uma chamada `media.frame` que devolva um quadro único;
o outro é mover o detector para dentro do `mediad`, assinando o ramo raw, rodando a alguns Hz e publicando o resultado da detecção no fluxo de estado.

> O segundo é a forma final: **a percepção fica ao lado do sensor, emitindo características em vez de transportar pixels**.

### Conclusões para quem replica

1. **A imagem do sistema não pode ser trocada à vontade** — precisa ter o kernel vendor da Rockchip (família Armbian)
2. A primeira coisa ao receber a placa é **ativar o nó da NPU e reiniciar**; caso contrário toda a inferência roda na CPU
3. Para treinar seu próprio modelo, **a partir de 150 quadros** já há precisão utilizável, a barreira é menor do que se imagina
4. Não espere conseguir agora obter quadros do robô para desenvolvimento adicional — **esta cadeia o próprio upstream ainda não completou**

## 8. Parâmetros-chave do lado do software (devem ser alinhados na réplica)

| Parâmetro | Valor | Descrição |
|---|---|---|
| Loop de controle | **50 Hz** | Herdado do protótipo (definido na Raspberry Pi Zero 2W), **nunca revalidado** no Radxa |
| Interface da política | `obs[1,61] → actions[1,14]` | Validada no carregamento; a versão antiga de 51 dimensões é rejeitada |
| `action_scale` | 0,9 (marcha) / 0,8 (patins) | |
| Ganho P de posição | **200** | ×0,8 em pé |
| Passa-baixa das ações | head **0,5** / legs **0,7** | **Deve ser igual ao do treinamento**, senão o desempenho da transferência cai |
| Adaptação à tensão | Desligada por padrão | Quando ligada, `scale × (7.4 / EMA medida)`, limitada a 6,0–9,5 V |

### Dois detalhes de engenharia que valem copiar

**1. Pouso suave preditivo (`limp_fall`)**

Não espera a queda para reagir, e sim **extrapola**: a gravidade projetada gira junto com o tronco, e sua taxa de variação é exatamente
`-(ω × g)`; usando os dados do giroscópio do mesmo bloco de 12 bytes do IMU, extrapola-se **300 ms**.
Quando o robô **já** está inclinado além de cerca de 26°, **e continua caindo**, e o ponto de queda extrapolado ultrapassa o limiar →
o ganho é imediatamente reduzido de 200 para **50**, deixando as juntas seguirem a força externa, num **pouso suave**.
Depois de estabilizar (julgado pelo giroscópio em repouso, não por temporizador), leva 600ms para puxar a postura de volta à de pé,
e só então devolve o controle à política de ficar em pé.

> A justificativa está muito bem escrita: a política de ficar em pé "é ótima para levantar, péssima para cair" —
> consegue levantar limpamente a partir de decúbito ventral/dorsal parado, mas numa queda dinâmica fica tentando repetidamente e falhando,
> brigando com o chão usando o ganho da marcha, e os motores pagam por cada tentativa.

**2. Os 2 Hz da detecção na NPU são um limite térmico**

> Texto original do comentário: *"2 is a thermal limit, not a preference"* — a plena velocidade chega a **95°C**,
> a CPU reduz o clock para **408 MHz**, e vira um robô que "para enxergar bem, anda mal".

## 9. O que fazer para replicar este sistema eletrônico por conta própria

### ✅ Comprar pronto

| Componente | Modelo | Observações |
|---|---|---|
| Controlador | **Radxa Zero 3W** | Módulo comercial, **não é placa customizada** |
| Servos | Dynamixel XL330 × 15 | |
| Bateria | **Sony NP-F550** + suporte | Bateria genérica de câmera, acessórios por toda parte. **Não compre a F970, não cabe** |
| Câmera | Raspberry Pi Camera v2 (IMX219) | |
| ToF | Módulo VL53L8CX (Stemma/Qwiic) | |

### 📥 Uma placa cujo projeto oficial é só baixar

**RPI Robot HAT — não precisa desenhar.**
[`pollen-robotics/elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT) (Apache-2.0)
tem o diretório `production/` com Gerber, BOM e coordenadas de posicionamento completos; basta fazer o pedido de fabricação e montagem SMT.

Se quiser simplificar (sem gravação nem alto-falante), também é possível não fazer a placa inteira — **mas não dá para só cortar sem compensar**:

- **O circuito de direção half-duplex do barramento dos servos é indispensável** (o conjunto de buffers tri-state U5/U6/U7; este texto, em §5B, já demonstrou que "o código não tem GPIO de controle de direção, esse circuito está na placa HAT") → é preciso ter à parte uma placa adaptadora de barramento da série ST/SC
- Distribuição de energia → um UBEC de 5V pronto
- ToF → conectar direto no i2c3

O custo é perder o áudio da placa e a identificação Pi HAT+. Para compras, veja [Análise de compras de eletrônica §6](电控采购清单.md#6-duas-pcbs).

### 🔧 A única placa que você precisa desenhar

**`imu_to_dxl`** — sem projeto público em toda a rede, é a **única que precisa ser reconstruída por você**.
LSM6DSV16X + MCU pequeno (escravo Dynamixel V2) + transceptor TTL half-duplex.
O protocolo e o layout de registradores de 12 bytes estão completos neste texto, basta implementar conforme.

### ⚠️ Armadilhas que exigem atenção

1. **i2c3 em conflito com o FUSB302** — usar o I2C em hardware nos pinos 3/5 faz perder a negociação USB-C PD
   (mas o carregamento comum de 5V continua funcionando). Veja a seção 4.
2. **A NPU vem desligada por padrão** — o Armbian não a ativa de fábrica; para rodar modelos rknn é preciso gravar um overlay e reiniciar.
3. **A câmera foi montada torta um quarto de volta** — no software é preciso `rotate=90`, feito pelo codificador de hardware, não use
   `videoflip` (que percorre cada quadro inteiro na CPU).
4. **O loop de controle de 50 Hz não foi validado no Radxa** — a própria oficial admite que é um número
   herdado da Raspberry Pi Zero 2W.

## 10. Conclusão: este sistema eletrônico é replicável

Eu havia avaliado antes que "a placa-mãe customizada RK3566 não se compra, e o PCB é um muro rígido" — **essa avaliação precisa ser corrigida**:

- O controlador é o **Radxa Zero 3W comercial**, não uma placa-mãe customizada
- **A placa HAT é totalmente open source oficialmente** (KiCad + Gerber + BOM), não é preciso desenhá-la
- A `imu_to_dxl` restante tem poucos componentes e protocolo totalmente restaurado, e é a única que você precisa fazer

**A barreira que realmente resta é o software**: o runtime em Rust, embora open source (Apache-2.0), está atrelado à
fiação específica do Radxa Zero 3W; se você seguir o mesmo controlador, **o runtime pode rodar diretamente**.

> Fontes dos dados: `duck-control/src/{model,imu,bus}.rs` de `pollen-robotics/microduck`,
> `deploy/robotd.toml`, `deploy/audio/*.dts`, `deploy/overlays/*.dts`,
> `tof/src/*.rs`, `mediad/src/*.rs`, `docs/project/media-bringup.md`.
