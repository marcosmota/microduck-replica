## 1. Visão geral: cinco módulos, só dois precisam ser feitos por você

```
                    ┌─────────────────────────────────────────┐
                    │  Cabeça (corpo rígido jaw_soft no MJCF)  │
                    │                                          │
   MIPI CSI ────────┤  ④ Câmera IMX219 + lente M12             │
   (cerca de 13mm,  │        ↕ mesmo corpo rígido, sem junta   │
    não passa pelo  │  ① Radxa Zero 3W    controlador principal│
    pescoço)        │        ↕ espaçamento do empilhamento 7,3mm, header de 40 pinos │
                    │  ② RPI Robot HAT    energia / áudio / barramento │
                    │        └─ porta Stemma ──► ⑤ módulo ToF  │
                    │  alto-falante                            │
                    └──────────────┬──────────────────────────┘
                                   │
                    ═══════════════╪══════ passa pelo pescoço de três graus de liberdade ══════
                     barramento dos servos (1 par) │ cabo de alimentação da bateria (+BATT)
                                   │
                    ┌──────────────┴──────────────────────────┐
                    │  Tronco (trunk_base)                     │
                    │   dois XL330 hip_yaw — cavidade interna quase toda ocupada │
                    │   ③ placa imu_to_dxl (no barramento dos servos) │
                    └──────────────┬──────────────────────────┘
                                   │
                     Bateria NP-F550 ─┘ presa externamente atrás e embaixo do corpo
                     dos 71mm de comprimento, cerca de 40mm ficam para fora da carcaça,
                     seguros por duas peças power_support que a prendem por fora
```

| # | Módulo | Em uma frase | Como obter |
|---|---|---|---|
| ① | **Radxa Zero 3W** | O cérebro. Roda Linux, a política de rede neural e a visão | 🛒 Comprar |
| ② | **RPI Robot HAT** | Quadro de energia + placa de áudio + interface do barramento dos servos | 🏭 **Open source oficial, mande fabricar** |
| ③ | **imu_to_dxl** | Disfarça um IMU de servo falso | ✏️ **Você precisa desenhar** |
| ④ | **Câmera IMX219** | Os olhos | 🛒 Comprar |
| ⑤ | **Módulo ToF** | Medição de distância em 8×8 zonas, não é LiDAR | 🛒 Comprar |

> ⚠️ **Três equívocos comuns**
> 1. **Não existe LiDAR.** O ToF é um módulo de medição de distância multizona (4×4 ou 8×8 zonas), não um radar.
> 2. **O áudio não é um módulo independente.** O codec, o amplificador e o microfone estão todos no HAT.
> 3. **O controlador principal não fica no tronco, fica na cabeça.** Este é o ponto mais fácil de errar e afeta diretamente o comprimento do flat cable que você compra.

## 2. ① Controlador principal · Radxa Zero 3W

**Para que serve**: roda o Linux Armbian, o runtime em Rust `robotd`, a inferência da política ONNX e a visão.
Em uma frase: **tudo, exceto acionar os motores, é feito por ele**.

| Item | Valor |
|---|---|
| SoC | Rockchip **RK3566**, quad-core Cortex-A55 @1,6GHz |
| NPU | 0,8–1 TOPS INT8, nó `npu@fde40000`, **desativada por padrão no Armbian**, é preciso aplicar um overlay |
| Formato | **65 × 30 mm**, formato Raspberry Pi Zero, header de 40 pinos |
| Sistema | Imagem Armbian **headless** |

**Por que esta placa e não uma Raspberry Pi**: ela é um **módulo comercial**, não uma placa-mãe customizada — isto é importante,
pois significa que a réplica não precisa fabricar a placa do controlador. A árvore de dispositivos (device tree) tem fixado `compatible = "radxa,zero-3w"`.

**Quais dos 40 pinos ela usa** (extraído do esquemático oficial do HAT):

| Pino | Uso | Dispositivo Linux |
|---|---|---|
| **GPIO14 / GPIO15** | **UART Tx / Rx do Dynamixel** | `/dev/ttyS2` @ 1 Mbps |
| **GPIO02 / GPIO03** | I²C — IMU + áudio + Stemma | `i2c3` @ 400 kHz |
| GPIO18 / 19 / 20 / 21 | Áudio PCM Clk / FS / Din / Dout | `i2s3_2ch` |
| GPIO06 | Detecção de desligamento (Switch off detection) | |
| GPIO22 | Pino de interrupção do BMI088 no HAT (**não usado pelo software**) | |
| GPIO00 / 01 | I²C de identificação do HAT (reservado) | ⚠️ Veja a seção do HAT |
| GPIO04/05, 08/09, 10/11 | I²C Stemma/QT adicionais | |
| MIPI CSI | Câmera | |

**Qual configuração comprar**: placa nua de 1G ou 2G **sem eMMC**, com um cartão microSD de 32 GB, apenas por canais oficiais. Testes e justificativas em [Análise de compras de eletrônica](电控采购清单.md#qual-configuração-comprar).
O material oficial indica 1 GB de memória e 32 GB de armazenamento (sem dizer que é eMMC). (Correção de 2026-10-12: o que se escrevia antes, "2G / 16G eMMC", era desnecessário.)

## 3. ② RPI Robot HAT — uma placa que faz quatro coisas

**Esta é a única placa totalmente open source oficial** ([`pollen-robotics/elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT),
Apache-2.0, com projeto KiCad + Gerber + BOM + coordenadas de posicionamento SMT).

**Especificações** (medidas no Gerber): placa de 4 camadas, **65,0 × 30,9 mm**, cantos arredondados R3,5, BOM com 47 linhas / 123 componentes,
dos quais 5 linhas / 9 componentes são DNP, restando **113 posições montadas**.

### Bloco funcional 1: distribuição de energia

```
Bateria NP-F550 ──► +BATT ──┬──► servos (alimentação direta, sem regulagem)
  2S, 6,6–8,2V              │
                            └──► U9 AP63205 + L4 6,8µH ──► Q2 / U10 LM5050-1 ──► +5V
                                   buck, 2A, Fsw 1,1MHz      diodo ideal + detecção de desligamento │
                                                                                        ├─► header de 40 pinos do controlador
                                                                                        ├─► amplificador PAM8406D
                                                                                        └─► U3 XC6206P182 → +1V8 (codec)
```

**Há aqui um fato contraintuitivo: os servos recebem a tensão bruta da bateria, não 5V.**

O valor nominal oficial do XL330 é **3,7–6,0 V, com 5,0 V recomendado**, mas aqui ele recebe **6,6–8,2 V**.
A evidência não é suposição, está escrita diretamente no esquemático: os pinos de alimentação dos quatro conectores Dynamixel J13/J14/J3/J11 ligam todos em `+BATT`,
com a anotação "3A max". E **a placa inteira tem apenas um buck (U9) e um indutor (L4)**; esse 5V é para o controlador
— o AP63205 de 2A não sustentaria 15 XL330 (cada um consome cerca de 1,5A em estol).

Detalhes em [A verdade sobre a tensão](执行器选型.md#-a-verdade-sobre-a-tensão-o-xl330-opera-em-sobretensão).

> Já o `+3V3` é **fornecido pelo controlador ao HAT pelo header de 40 pinos**, não é gerado pelo próprio HAT.

### Bloco funcional 2: barramento dos servos (TTL half-duplex)

Servos de barramento como Dynamixel / Feetech são **half-duplex de um fio** — o mesmo fio transmite e recebe, alternando por controle de direção.

| Componente | Função |
|---|---|
| **U6 `SN74LVC1G125`** | Buffer tri-state, direção de transmissão |
| **U7 `SN74LVC1G126`** | Buffer tri-state, direção de recepção |
| **U5 `74LVC1G08`** | Porta AND, participa da lógica de direção |
| **U8 `SIT3088E`** | Transceptor RS-485 (para as duas portas de 4P) |
| **TH1 100R** | Termistor, proteção contra sobrecorrente |

A direção é controlada por `Dynamixel_dir`; a anotação oficial diz **"Dynamixel_dir is based on Tx"** — a direção é derivada automaticamente do sinal de transmissão.

**Quatro conectores, de dois tipos**:

| Designador | Tipo | Quem usa |
|---|---|---|
| **J13 / J14** | **JST EH 3P** (TTL) | **Os XL330 do Microduck usam estes dois**, via TH1 até `+BATT` |
| J3 / J11 | JST EH 4P (RS-485) | Acionados pelo U8, direto em `+BATT` |

> 💡 **O JST EH tem passo de 2,5 mm**, e o cabo dos servos Feetech indica o **terminal 5264**, também de 2,5 mm.
> No mercado chinês, "5264" é basicamente o nome genérico do 3P de 2,5 mm — é muito provável que encaixe direto, mas
> recomenda-se confirmar com a peça real os detalhes da trava do invólucro.

### Bloco funcional 3: áudio

| Componente | Função | Endereço |
|---|---|---|
| **U2 `TLV320AIC3104`** | Codec de áudio, dados I²S + controle I²C | i2c3 `0x18` |
| **U1 `PAM8406D`** | Amplificador classe D | |
| **MK1** | Microfone MEMS na placa (LCSC `C7587901`, modelo não informado oficialmente) | |
| J1 | Borne Wago sem parafuso, para **alto-falante de 5W** | |
| J2 / J9 | Bornes Wago, para microfone externo | |

Clock de áudio: MCLK de cristal fixo de 12 MHz, sysclk I²S de 12,288 MHz (256 × 48 kHz).

> **Se você não precisa de gravação nem de alto-falante, todo este bloco pode ser dispensado.**

### Bloco funcional 4: expansão de sensores

- **J5–J8**: JST SH 1,0 mm 4P (Qwiic / Stemma QT) — o ToF é conectado aqui
- **U11 `BMI088`**: ⚠️ **está soldado, mas o software não o usa de forma alguma**. O comentário original da device tree diz `dormant`,
  `unused but still connected`. Quando se diz por aí que o Microduck "tem dois IMUs", é a este que se referem
- **U4 `CAT24C32`** EEPROM: ⚠️ **DNP, não montado** — portanto esta placa **não é um HAT autoidentificável**,
  embora o esquemático escreva "HAT Identification: I2C add. 0x50 / Standard Class HAT+"

### Esta placa não se compra pronta, o que fazer

**A Pollen não vende separadamente**, só o robô completo. Há dois caminhos:

1. **Fabricação fiel** — leve o Gerber oficial + BOM + coordenadas de posicionamento à JLC (嘉立创). Placa de 4 camadas + SMT, a partir de algumas centenas de yuans, com quantidade mínima.
2. **Substituir por módulos prontos** — uma placa adaptadora half-duplex ST/SC de ¥22 + um UBEC substituem as duas funções indispensáveis, "barramento dos servos" e
   "distribuição de energia", e o ToF vai direto no i2c3. O custo é perder o áudio da placa. Veja [Análise de compras de eletrônica](电控采购清单.md#6-duas-pcbs).

## 4. ③ imu_to_dxl — o truque mais inteligente de todo o sistema eletrônico

**Esta placa faz uma única coisa: disfarça o IMU de servo falso.**

Ela é um **STM32G031F8P6 + LSM6DSV16X** (IMU de seis eixos da ST) + buffer half-duplex,
e para o exterior se apresenta como um escravo no barramento dos servos, com **ID = 200**.

### Por que tanto rodeio

A abordagem intuitiva seria ligar o IMU por I²C ou SPI diretamente ao controlador. Mas isso tem um problema:

**Os dados do IMU e os dos servos viajam por dois caminhos diferentes, e os instantes de amostragem não se alinham.**

A política roda a 50 Hz, e a cada tick é preciso conhecer ao mesmo tempo "a postura do corpo" e "os ângulos das 15 juntas".
Se o IMU vai por I²C e os servos por UART, há alguns milissegundos de jitter entre os dois — e o jitter contamina diretamente a entrada da política.

A solução da Pollen foi **fazer o IMU falar a língua dos servos**; assim, o host envia **um único `sync_read`** por tick
e recebe de volta ao mesmo tempo a postura do IMU + 15 posições de servos, com **timestamps naturalmente alinhados**.

### Protocolo e registradores

| Item | Valor |
|---|---|
| Protocolo | Dynamixel **Protocol V2** |
| ID | **200** |
| Baud rate | **1 Mbps** (registrador EEPROM `baud_rate = 3`) |
| Registrador inicial | **124** |
| Comprimento | **12 bytes** |

Layout dos 12 bytes:

| Offset | Conteúdo |
|---|---|
| `0..6` | gyro x/y/z, contagem bruta `i16` little-endian, faixa **±500 dps**, **17,5 mdps/LSB** |
| `6..12` | Quaternion SFLP x/y/z, **meia precisão IEEE fp16**; `w = √(1 − x² − y² − z²)` |

**Note que `w` não é transmitido** — é recalculado no lado do host pela restrição de quaternion unitário, economizando 2 bytes.

**SFLP** é um **bloco de fusão de sensores em hardware** dentro do chip LSM6DSV16X, que emite diretamente o quaternion de rotação de jogo
— o host não precisa executar a fusão de postura por conta própria.

### No total, 16 dispositivos no barramento

```
ID  10 11 12 13 14   perna direita
ID  20 21 22 23 24   perna esquerda
ID  30 31 32 33 34   pescoço / cabeça / boca
ID  200              placa imu_to_dxl
```

15 servos + 1 placa de IMU = **16 dispositivos, todos lidos de volta com um único `sync_read`**.

### O que observar ao replicar

- **O protocolo e o layout dos registradores foram totalmente restaurados**, basta implementar conforme ([Engenharia reversa da solução de hardware](硬件方案逆向.md))
- **Use conector 3P de passo 2,5 mm** (JST EH / 5264)
- **Capacitor de entrada com tensão nominal ≥25 V** — com a bateria cheia o barramento chega a 8,4 V, e a especificação de 10 V não dá margem (o MLCC ainda sofre queda de capacitância por polarização DC)
- **O pino CS precisa de pull-up** — veja o caso real na próxima seção
- **Adicione TVS na linha DATA** — conectar/desconectar servos com o sistema energizado é rotina

## 5. ④ Câmera IMX219

Interface MIPI CSI, 8 megapixels. O overlay da device tree usa `radxa-zero3-rpi-camera-v2`,
e a configuração do ISP é `SENSOR = imx219`.

**Duas armadilhas:**

1. **É girada 90°, não montada invertida a 180°.** O código diz
   `/// 90, because the head camera is mounted a quarter turn off, and this is the one place
   that fact is written down.` Alguns materiais antigos dizem 180; esses são dados da **máquina alpha**.
2. **Compre o flat cable mais curto.** A câmera e o controlador **estão no mesmo corpo rígido, a cerca de 13 mm, sem junta entre eles** —
   o cabo MIPI não passa pelo pescoço. 4–15 cm bastam, não compre de 30 cm.

> ⚠️ A documentação oficial da Radxa só diz "1x4-lane MIPI CSI", **sem informar o número de pinos nem o passo**.
> Mas a placa tem formato Pi Zero e o conector CSI fica no mesmo lado do Micro HDMI, então **muito provavelmente é o estreito de 22 pinos e 0,5 mm**,
> enquanto os módulos IMX219 genéricos vêm com o padrão de 15 pinos — tenha à mão um cabo adaptador (alguns reais).

## 6. ⑤ Módulo ToF

**Não é LiDAR.** É um chip de medição de distância multizona ST FlightSense, que emite uma **matriz de distâncias 8×8**.

| Item | Valor |
|---|---|
| Modelo | **VL53L5CX ou VL53L8CX**, o firmware identifica automaticamente pelo revision ID (`0x02` = L5cx, `0x0C` = L8cx) |
| Interface | I²C, no **i2c3 @ 400 kHz** |
| Endereço | **`0x29` ou `0x52`** (os dois candidatos são testados) |
| Conexão física | **JST SH 1,0 mm 4P** no HAT (Qwiic / Stemma QT) |
| Taxa de quadros | 15 Hz |

> ⚠️ **Não compre um VL53L0X por engano** — ele faz medição de **ponto único**, e o firmware não o reconhece.
> **O VL53L7CX também não é o L8CX** (o L7 é outro chip, com campo de visão de 90°).

## 7. O que acontece em um tick

A política roda a 50 Hz, ou seja, **um ciclo a cada 20 ms**:

```
   ① Um sync_read                    ttyS2 @ 1 Mbps
      ├─ ID 200  → gyro + quaternion  ┐
      ├─ ID 10~14 → 5 ângulos da perna direita ├ 12 bytes × 16 dispositivos
      ├─ ID 20~24 → 5 ângulos da perna esquerda │  timestamps naturalmente alinhados
      └─ ID 30~34 → 5 de pescoço/cabeça/boca   ┘

   ② Monta o vetor de observação de 61 dimensões

   ③ Inferência da política ONNX (rede pequena de 775 KiB) → ação de 14 dimensões

   ④ Adaptação à tensão: scale × (7,4 / EMA da tensão medida da bateria)
      — quando a bateria cai de 8,4V para 6,5V, o mesmo PWM gera um torque bem diferente; sem compensação a política deriva

   ⑤ Um sync_write, enviando as 14 posições-alvo
```

Em paralelo, rodam ainda: o ToF no **i2c3** (15 Hz) e o codec de áudio, e a câmera no **MIPI CSI**.

> ⚠️ **O orçamento de 20 ms é apertado, e não é problema só da Feetech.**
> O código-fonte oficial diz: o XL330 sai de fábrica com `return_delay_time = 250`, ou seja, **500 µs de atraso de virada por dispositivo**,
> "Across 16 devices that is **8 ms per tick — 40% of a 20 ms budget**".
> A solução oficial é **escrever 0** neste registrador.
> Ao trocar por qualquer outro servo, este passo precisa ser refeito e medido na prática.

## 8. Seguindo a rota Feetech, o que muda

Muita gente (inclusive este repositório) avalia substituir o XL330 por servos Feetech. Impactos, por ordem de gravidade:

| Impacto | Descrição |
|---|---|
| 🔴 **Os 9 políticas ONNX oficiais provavelmente deixam de funcionar** | Com outro servo, a curva de torque, a massa e talvez até a relação de redução são diferentes. **É preciso retreinar** (exige GPU CUDA ou HF jobs) |
| 🟡 **A temporização do barramento precisa ser medida** | A Feetech usa o conjunto de instruções próprio STS/SCS (incluindo `0x82 SYNC READ`), com formato de pacote diferente. **Mas não suponha que será necessariamente mais lento** — o caminho Dynamixel oficial também tem atraso de virada por dispositivo (veja acima). A primeira coisa ao receber é rodar um benchmark, com uma **placa de depuração FE-URT-1** |
| 🟡 **O `imu_to_dxl` precisa ser reposicionado** | O protocolo do barramento mudou; esta placa ou passa a emular um escravo Feetech, ou abandona o projeto de "ficar no barramento" e o IMU vai por SPI direto. **Recomendação: hardware inalterado, firmware com dois protocolos** — a camada física é idêntica (TTL half-duplex de um fio / 1 Mbps / 3 fios), a diferença está no **formato do pacote** e nos **valores padrão de fábrica**; veja "Comparação dos protocolos Feetech STS/SCS" em [Engenharia reversa da solução de hardware](硬件方案逆向.md) |
| 🟢 **A tensão, ao contrário, fica mais adequada** | O Feetech HD-1910 aceita nativamente 5–8,4 V, sem a sobretensão que o XL330 sofre |

## 9. Como conferir por conta própria: cinco verificações antes de replicar

**Esta seção é mais importante do que todo o resto acima.**

Materiais de projetos open source ficam desatualizados e têm erros, e esquemáticos gerados por IA mais ainda. Abaixo estão as ações de verificação
que este repositório consolidou na prática — cada uma corresponde a um tropeço real.

### 1. Definição de pinos: consulte a tabela de pinos do datasheet e confira um a um

**Caso real:** este repositório recebeu um PR com o esquemático do `imu_to_dxl`. O desenho estava bem completo, mas ligou errado os pinos do
LSM6DSV16X — conferindo a **Tabela 1 do ST DS13510 Rev 1** (página 10), constatou-se:

| Pino | Definição no datasheet | O que o PR desenhou |
|---|---|---|
| **12** | **CS** (chip select) | ❌ Deslocado |
| **13** | **SCL** (clock SPI) | ❌ Deslocado |
| **14** | **SDA** (dados SPI) | ❌ Deslocado |
| **2 / 3** | **Interface auxiliar SDx / SCx**, o datasheet exige **ligar ao GND** quando não usada | ❌ Tratada como interface principal |

A placa fabricada assim **não funciona**. E descobrir isso exige uma só coisa: **abrir o datasheet, ir à tabela de pinos e conferir linha por linha**.

> **Desenhar o esquemático sem ler o datasheet é o mesmo que não tê-lo desenhado.** Esta frase não admite exceção.

### 2. Margem de tensão: tensão nominal de cada capacitor vs. a tensão real do barramento

No mesmo PR, o capacitor de entrada estava especificado para **10 V**, e o barramento com a bateria cheia tem **8,4 V**. Parece haver margem, mas:
- O MLCC tem **efeito de polarização DC**; 8,4 V sobre um MLCC de 10 V pode derrubar a capacitância efetiva em mais da metade
- A bateria e a força contraeletromotriz do motor geram picos

**Regra: a tensão nominal deve ser pelo menos 2 vezes a tensão de trabalho.** Para um barramento de 8,4 V, use 25 V.

### 3. Estado na energização: qual o nível dos pinos de seleção de modo no instante em que se liga

O nível do pino CS do LSM6DSV16X **na energização define se ele opera em SPI ou I²C**. Se o CS estiver flutuando,
o estado no instante da energização é indeterminado — às vezes funciona, às vezes não, o tipo de bug mais difícil de rastrear.

**Adicione um pull-up de 10 kΩ a 3V3** para travar o modo SPI.

### 4. Rode o ERC, e rode até 0 erros e 0 avisos

O KiCad executa pela linha de comando:

```bash
kicad-cli sch erc --output erc.rpt your.kicad_sch
```

Problemas reais comuns: pino de alimentação sem fonte que o acione (falta `PWR_FLAG`), dois Power output colidindo,
coordenadas de pino fora da grade de conexão (parece conectado, mas não está).

### 5. Verificação cruzada: endereços e registradores no código-fonte do software vs. o hardware

O software do Microduck é open source, e **o código é a especificação**. Cada endereço no hardware pode ser encontrado no código:

| Hardware | Evidência no software |
|---|---|
| Codec de áudio `0x18` | `deploy/audio/i2c3-pihat.dts` |
| ToF `0x29` / `0x52` | `ADDRESS_CANDIDATES` em `tof/src/main.rs` |
| Placa de IMU ID 200 | `IMU_DXL_ID` em `duck-control/src/model.rs` |
| Atribuição de IDs dos servos | idem, `JOINT_IDS` |
| i2c3 400 kHz | `clock-frequency` em `i2c3-pihat.dts` |
| BMI088 não usado | comentário em `i2c3-pihat.dts`: `dormant`, `unused but still connected` |

**Se não batem, um dos lados está errado.**
