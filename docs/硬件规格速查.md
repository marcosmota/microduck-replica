## Diagrama de blocos do sistema

```
                ┌──────────────────────────────┐
                │   Radxa Zero 3W (RK3566)     │  65 × 30 mm
                │   Armbian · kernel 6.1.115    │  formato Pi Zero
                └──┬────────┬─────────┬────────┘
      /dev/ttyS2   │        │ 40-pin  │ MIPI CSI
      1 Mbps TTL   │        │  I2C3   │
    ┌──────────────┘        │ 400kHz  └── câmera IMX219 (girada 90°)
    │                       │
    │              ┌────────▼─────────────────┐
    │              │  Pollen RPI Robot HAT    │  placa própria 65×30mm (open source)
    │              │   ├ TLV320AIC3104  0x18  │  codec de áudio
    │              │   ├ BMI088   0x19/0x68   │  soldado mas sem uso
    │              │   └ Stemma J5 → ToF 0x29 │  VL53L5CX/L8CX
    │              │  a bateria alimenta via esta placa │
    │              └──────────────────────────┘
    │
════╪══════════ Barramento Dynamixel · Protocol V2 · 1 Mbps ══════════
    │
    ├── 15 × XL330   ID perna esq. 20-24 / pescoço-cabeça-boca 30-34 / perna dir. 10-14
    └── placa imu_to_dxl v2   ID 200   ← LSM6DSV16X
```

**Princípio central de projeto**: um único barramento resolve tudo. O IMU não usa I2C: é feito como escravo Dynamixel no barramento dos servos,
e é lido no **mesmo `sync_read`** que os 15 servos. A tensão da bateria também dispensa medidor de carga:
lê-se diretamente a tensão de alimentação que os servos reportam.

## Controlador principal

| Item | Valor |
|---|---|
| Módulo | **Radxa Zero 3W** — módulo comercial, **não é uma placa-mãe customizada** |
| SoC | **RK3566** (4× Cortex-A55 + Mali-G52 + NPU) |
| Dimensões | 65 × 30 mm, formato Pi Zero, header de 40 pinos compatível com Raspberry Pi |
| Sistema | **Armbian** (família Debian), kernel vendor 6.1.115 |
| Inferência da política | ONNX Runtime ≥1.23 (instala-se a 1.28.0), carregado via `dlopen` |
| Inferência na NPU | rknn-toolkit2 — **desativada por padrão no Armbian**, é preciso gravar um overlay e reiniciar |

> Base: device tree `compatible = "radxa,zero-3w", "rockchip,rk3566"`;
> "radxa" aparece 182 vezes em todo o repositório.

### Por que se ouve dizer que é uma Raspberry Pi

1. A placa própria **se chama "RPI Robot HAT"**
2. Formato Pi Zero + header de 40 pinos compatível com Raspberry Pi
3. A câmera é a **Raspberry Pi Camera v2** (IMX219)
4. **Na fase de protótipo, de fato usou-se uma Raspberry Pi Zero 2W** — comentário em `robotd.toml`: o loop de controle de 50 Hz
   *"is inherited from the prototype, where it was chosen on a Raspberry Pi Zero 2W"*

Seu antecessor, o Open Duck Mini v2, **ainda hoje usa a Raspberry Pi Zero 2W**, porque não faz visão nem streaming WebRTC.

### Por que precisa ser um SoC Linux e não um MCU

É preciso rodar ao mesmo tempo: inferência de política ONNX @50Hz, codificação H.264 720p30 por hardware + streaming WebRTC,
detecção de objetos na NPU, controle de congestionamento do GStreamer (consome 7,6% de um núcleo), controle Bluetooth + app de celular + WiFi.
**STM32 / ESP32 não dão conta.**

## Atuadores e barramento

| Item | Valor |
|---|---|
| Motor | **Dynamixel XL330 × 15** (cerca de 18 g cada) |
| Camada elétrica | **TTL half-duplex de um fio** (3 fios: dados + VDD + GND), 3,3V |
| Protocolo | **Dynamixel Protocol V2** |
| Taxa | **1 Mbps** (EEPROM `baud_rate = 3`) |
| Porta | `/dev/ttyS2` = **UART2 do RK3566, pinmux M0** |
| Dispositivos conectados | **16**: 15 servos + 1 placa de IMU |
| Loop de controle | **50 Hz**, um `sync_read` cobre os 16, registradores 124–136 |
| Biblioteca Rust | [`rustypot`](https://github.com/pollen-robotics/rustypot) |

> ❗ **Não é RS232 nem RS485.** RS485 é diferencial de dois fios, usado nas séries XM/XH do Dynamixel.
> O XL330 é TTL half-duplex de um fio. Buscando `rs485|rs232|direction pin` em todo o repositório, **zero ocorrências** —
> o código não tem GPIO de controle de direção; a troca de direção é feita por um circuito de direção automática em hardware (na placa HAT).

### Atribuição de IDs dos servos

```
Perna esq.   20 21 22 23 24    hip_yaw / hip_roll / hip_pitch / knee / ankle
Pescoço-cabeça-boca 30 31 32 33 34    neck_pitch / head_pitch / head_yaw / head_roll / mouth
Perna dir.   10 11 12 13 14    (espelho da perna esquerda)
Placa IMU    200
```

**O 15º servo é a boca (ID 34, índice 9).** Todas as políticas são `obs[1,61] → act[1,14]`,
e o vetor de ações **pula esse índice** — a boca é controlada pela lógica de nível superior, não pela política.

### Confiabilidade do barramento (medição oficial)

| Indicador | Valor | Origem |
|---|---|---|
| Taxa de perda de pacotes | **cerca de 8 por minuto ≈ 0,27%** | *"Measured on a bench robot at ~8 drops a minute"* |
| Avaliação oficial | *"One dropped Dynamixel transaction is **ordinary**"* | `robotd/src/main.rs` |
| Sintoma | Pequenos espasmos aleatórios (uma leitura perdida faz a política parar um tempo e voltar à postura de hold) | idem |
| Tolerância a falhas | `COAST_TICKS = 3` desliza 60ms com a última boa amostra | idem |
| Limite tolerado | `max_consecutive_errors = 10` | `robotd.toml` |
| Estabilidade do loop | `missed=3` / 15022 ticks, mantém 50,0 Hz | `roadmap.md` |
| Dados do IMU degradados | Existe um `StaleImuTracker` dedicado, com o comentário *"Known to happen"* | `bus.rs` |

A utilização do barramento é estimada em **cerca de 25%** (cerca de 500 bytes/tick ÷ 1 Mbps ÷ 20ms) —
**o gargalo não é a largura de banda, é a integridade do sinal e o ponto único de falha**: sinal single-ended de 3,3V, 15 servos em daisy chain,
chicote passando por um pescoço com flexão dinâmica, e ao lado a fonte de ruído do PWM dos motores.

## Duas placas próprias da Pollen (uma open source, outra a desenhar)

### ① `imu_to_dxl` v2 — poucos componentes, a mais fácil de fazer por conta própria

| Item | Valor |
|---|---|
| Chip do IMU | **LSM6DSV16X** (ST de 6 eixos, com bloco de fusão de postura em hardware SFLP) |
| Interface | **Barramento Dynamixel** (não I2C) |
| ID no barramento | **200** |
| Endereço do registrador | **124** |
| Leitura no loop de controle | 12 bytes |
| Bloco completo de diagnóstico | 20 bytes (inclui ainda aceleração bruta, contador de amostras, flags de estado) |

**Layout do bloco de 12 bytes**

| Bytes | Conteúdo |
|---|---|
| `0..6` | gyro x/y/z, `i16` little-endian, ±500 dps, **17,5 mdps/LSB** |
| `6..12` | Quaternion SFLP x/y/z, **IEEE fp16**; `w = √(1 − x² − y² − z²)` |

**O que é preciso para fazer por conta própria**: LSM6DSV16X + um MCU pequeno para atuar como escravo Dynamixel V2
(STM32G0/G4, CH32V203, ESP32 servem) + transceptor TTL half-duplex, com alimentação tirada do barramento.

### ② Pollen RPI Robot HAT — já open source oficialmente, basta mandar fabricar

**65,0 × 30,9 mm, espessura 1,0 mm, placa de 4 camadas** (obtidos do KiCad e do Gerber oficiais, veja a [BOM](../BOM.md)). Os 65,02 × 30,02 × 0,84 medidos na malha STL são uma aproximação de simulação, **não use para fazer o pedido**. Conecta-se a um header de 40 pinos.

| Componente | Endereço I2C | Descrição |
|---|---|---|
| **TLV320AIC3104** | `0x18` | Codec de áudio da TI, dados I2S + controle I2C |
| **BMI088** | `0x19` / `0x68` | **Soldado mas sem uso** (texto original do comentário: "dormant") |
| **ToF** | `0x29` | Não está na placa, conectado externamente via **Stemma J5** |

- I2C: **pino 3 / pino 5** do header de 40 pinos (`GPIO1_A0`=SDA, `GPIO1_A1`=SCL), **400 kHz**
- Pull-up: **um par de 10k, R12/R13**
- Clock de áudio: MCLK **12 MHz**, sysclk I2S **12,288 MHz** (256×48kHz)
- O microfone vai em **Mic3R** (PGA direito mono), as demais entradas ficam todas desligadas
- **A alimentação interna do robô passa por esta placa**

## Sensores

| Tipo | Modelo | Interface | Observações |
|---|---|---|---|
| IMU | **LSM6DSV16X** | Barramento Dynamixel ID 200 | O SFLP no chip gera o quaternion, o host não faz fusão |
| ToF | **VL53L5CX / VL53L8CX** | I2C `0x29` @ i2c3 | 15 Hz, medição multizona |
| Câmera | **IMX219** (Raspberry Pi Camera v2) | MIPI CSI, I2C `0x10` | **Girada 90°**, veja [Engenharia reversa da solução de hardware](硬件方案逆向.md#7-sensores) |

- O sensor da câmera é fixado no modo 1920×1080@30 (evitando o limite de 21 fps do modo padrão na inicialização),
  com saída escalada pelo ISP, padrão 720p30 @ 2 Mb/s
- A codificação usa o **codificador de hardware Rockchip MPP** → WebRTC
- HFOV de cerca de 62°

## Alimentação e bateria

| Item | Valor |
|---|---|
| Bateria | **Sony NP-F550** (bateria de câmera série L). ⚠️ O nome da malha upstream `np_f970` induz a erro; as dimensões medidas são as da F550 |
| Configuração | **2S íon-lítio**, nominal 7,2 V |
| Cheia (sob carga) | **8,2 V** |
| Vazia (sob carga) | **6,6 V** |
| Medidor de carga | **Não há** |
| ADC | **Não há** |

> Texto original do comentário: *"There is no fuel gauge and no ADC. The only measurement available is
> what the servos report as their own supply."*

**A tensão é lida diretamente pelo protocolo Dynamixel, a partir da tensão de alimentação que os servos reportam** — ou seja, "a bateria vista pelo barramento",
que cai sob carga e se recupera em repouso. Por isso 6,6–8,2 V é a **faixa utilizável sob carga**, não a faixa química da célula.

Quando a EMA da bateria (constante de tempo de cerca de 10 segundos) cai a 6,6 V → **senta com elegância e desliga automaticamente**.

> 💡 Amigável para a réplica: **não é preciso projetar nenhum circuito de monitoramento de bateria.**

## Parâmetros que o software precisa respeitar

| Parâmetro | Valor | Descrição |
|---|---|---|
| Loop de controle | **50 Hz** | Herdado do protótipo Raspberry Pi, **nunca revalidado no Radxa** |
| Interface da política | `obs[1,61] → act[1,14]` | Validada no carregamento; a versão antiga de 51 dimensões é rejeitada |
| `action_scale` | 0,9 (marcha) / 0,8 (patins) | |
| Ganho P de posição | **200** | ×0,8 em pé |
| Passa-baixa das ações | head **0,5** / legs **0,7** | **Deve ser igual ao do treinamento**, senão a transferência degrada |
| Adaptação à tensão | Desligada por padrão | `scale × (7.4 / EMA medida)`, limitada a 6,0–9,5 V |

## Três armadilhas pelas quais todos passam

1. **O Armbian roda por padrão um console de login na UART2** — o `agetty` do `serial-getty@ttyS2`
   ocupa a porta serial. É preciso `systemctl mask serial-getty@ttyS2`.
   A solução oficial foi descobrir isso com `fuser -v /dev/ttyS2`.

2. **O i2c3 disputa pinos com o FUSB302** — o i2c3 do RK3566 na DTB original usa o pinmux M1
   para atender o controlador USB-C PD; para usar o M0 dos pinos 3/5 é preciso desativar o fusb302, **perdendo a negociação PD**.
   Felizmente o FUSB302 apresenta Rd no CC por padrão ao ligar, então o carregamento comum a 5V continua funcionando.

3. **A NPU vem desligada por padrão** — o Armbian não a ativa de fábrica; para rodar modelos rknn é preciso gravar um overlay e reiniciar.

## Conclusão

**Nenhuma parte deste hardware é irreplicável.** O controlador é um módulo comercial; das duas placas próprias da Pollen,
a **placa HAT é totalmente open source oficialmente** (KiCad + Gerber + BOM + coordenadas de posicionamento, basta baixar e mandar fabricar),
e a única que realmente precisa ser desenhada por você é a `imu_to_dxl` — que tem poucos componentes e protocolo totalmente restaurado.

A barreira real é o **custo** (15 XL330 custam mais que o preço de venda do robô completo), não a técnica.

### ⚠️ A contradição: o oficial diz 2 IMUs, o software usa só 1

A especificação oficial diz **"2× IMUs (body and head)"**, mas no código-fonte:

- **Só o LSM6DSV16X está em uso** — `imu.rs` abre dizendo *"One IMU, one code path"*
- O **BMI088** na placa HAT está marcado na device tree como **"dormant"**,
  **"(unused but still connected)"**

**Conclusão: o segundo IMU está fisicamente soldado na placa, mas o software de fábrica não o usa.** Na réplica pode ser omitido.

## Situação do open source: posição oficial (atualização de 2026-08)

> Texto original da reportagem da CNX Software:
> *"While the Microduck's software stack is open source, nothing was said about the
> mechanical and hardware design files, and **Pollen Robotics told the press not to
> refer to the robot as 'open-source hardware' (for now)**."*

**Esta frase deve ser interpretada com cuidado.** O que a oficial recusa é o **rótulo** de chamar o robô completo de "hardware open source",
o que não significa que nenhuma placa tenha sido publicada — de fato, **a placa RPI Robot HAT é totalmente open source**
([`elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT), Apache-2.0,
com projeto KiCad, Gerber, BOM e coordenadas de posicionamento). O que realmente não foi publicado é a placa `imu_to_dxl`,
o CAD mecânico editável, a BOM do robô completo e a documentação de montagem.

Aquele **"(for now)"** deixa uma porta aberta, sem dar prazo.

> Errata 2026-09-03: este texto antes dizia "o hardware não ser open source é uma linha traçada ativamente pela oficial", formulação forte demais, já corrigida.

> bateria NP-F550 · frequência de controle 50 Hz

**Totalmente consistente com as conclusões da engenharia reversa deste repositório**, inclusive o ponto mais crítico, o **Radxa Zero 3W** —
dois caminhos independentes chegaram à mesma resposta, o que eleva bastante a credibilidade.

> 📌 **Atenção: até 2026-08-31 não havia nenhuma unidade física no mercado** (só serão enviadas antes do Natal).
> Portanto todos os "teardowns" atuais são **inferências baseadas em software e especificações públicos**, não desmontagens físicas.
