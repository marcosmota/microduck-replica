## Compras

**Não compre a bateria NP-F970, é a NP-F550**
O arquivo de malha do upstream chama-se `np_f970.stl`, mas as medidas dão 39 × 21 × 71 mm, que é o tamanho da F550. A F970 de verdade tem cerca de 60 mm de espessura e **não cabe**, e seus 300 g consumiriam um terço do orçamento de peso do robô completo.
→ Compre a NP-F550 (2S, 6,6–8,4 V). Detalhes na [BOM](BOM.md).

**O cabo do Feetech HD-1910 é de 2,0 mm, mas a porta da placa de depuração Feetech não é: para configurar o ID é preciso fazer ligação com fio solto**
O cabo original do HD-1910 é AMP2.0-3P (passo de 2,0 mm). A porta TTL da placa de depuração FE-URT-2 é maior que isso e o conector **não encaixa**; a placa também não tem porta de 2,0.
→ Se precisar configurar o ID no mesmo dia, **corte um cabo de servo** (sacrificando um dos 15) e ligue os três fios soltos assim:

```
舵机线                  FE-URT-2
脚 1  Signal    →   S    焊到板背面白口 S 脚的焊点上（临时也可镀锡后直接插进 S 孔）
脚 2  Vcc       →   V1   蓝色接线端子
脚 3  GND       →   G    蓝色接线端子
```

**O fio do meio é sempre o V** (Feetech e Dynamixel coincidem nisso); se S e G forem trocados não queima, só não se comunica, basta inverter.
**Só queima se o V for ligado errado.** Para configurar o ID sem carga, os 5 V do USB bastam (o HD-1910 funciona a partir de 4 V): primeiro meça com o multímetro se há 5 V entre G e V1 no borne azul; se não houver, mexa naquela chave.
→ O procedimento correto é comprar alguns cabos "terminal PH2.0 3P" e alguns cabos com o terminal da especificação da placa e soldá-los entre si, formando um cabo adaptador. Antes de comprar, olhe a caixa do servo, às vezes vem um incluído.
→ Vale avisar a Feetech diretamente: a versão oficial inclui ou não um cabo adaptador?

**A ordem dos pinos do Feetech é exatamente oposta à do Dynamixel**
Feetech HD-1910: `1=Signal 2=Vcc 3=GND`. Dynamixel XL330: `1=GND 2=Vcc 3=Signal`.
→ Felizmente os dois têm passos diferentes (2,0 vs 2,5 mm) e não encaixam um no outro. Resta só a possibilidade de crimpar o cabo ao contrário por conta própria: depois de crimpar, confira com o multímetro.

**Não use o HL-2915 como referência**
O Feetech HL-2915-C002 é um servo de 9–14 V; uma bateria 2S (máximo 8,4 V) **não consegue acioná-lo**, e a ordem dos pinos dele ainda é oposta à do HD-1910.
→ Este projeto só reconhece o HD-1910-C001.

**A bateria cheia a 8,4 V é exatamente o limite superior de tensão do HD-1910**
A faixa de operação do HD-1910 é 4–8,4 V. A NP-F550 cheia dá 8,4 V, **margem zero**. Só volta à zona segura quando a queda sob carga leva a tensão para 6,6–8,2 V.
→ Logo após carregar, não faça teste de travamento (stall) direto. Para armazenamento prolongado, guarde a 3,8 V/célula. Antes de montar o robô, ative a proteção de sobretensão dos servos.

**A Radxa Zero 3W de especificação baixa é uma placa pelada**
A versão de 2 GB sem eMMC **não tem barra de pinos soldada nem armazenamento**, só inicia por microSD.
→ Compre por conta própria uma barra de pinos 2×20 (2,54 mm, vertical; compre colorida, fica mais fácil contar os pinos) e um microSD de **alta durabilidade** (SanDisk High Endurance / Hikvision PLUS, 32 ou 64 GB; compre dois, um para backup).

**Não injete alimentação externa no terminal V1 da URT-2**
A chave DIP da placa é a seleção de nível TTL (3,3 / 5 V), **não** é um comutador de alimentação. Ao conectar o USB, o V1 já tem 5 V; não está claro como ele se liga ao USB, pode ser direto. Injetar 7,4 V no V1 corre o risco de realimentar o computador ou a Radxa.
→ A alimentação externa vai direto no V e no G do servo, o G da URT-2 também vai ao negativo para aterramento comum, e o V1 fica livre. A URT-2 cuida só do sinal.

**Todos os servos Feetech saem de fábrica com ID 1**
Se os 15 forem conectados juntos, todos respondem e não dá para distinguir quem é quem.
→ **Ao definir o ID, conecte um servo de cada vez.** Depois de alterar, cole uma etiqueta (nome da junta + ID), desconecte e passe para o próximo. Passos e tabela de IDs em [registro de depuração · configuração do servo](调试记录.md#configuração-dos-servos--passo-a-passo-ao-receber-as-peças).

**Módulo ToF: aquela placa L8CX não cabe na carcaça do rosto, e o firmware não reconhece o L7CX**
Sintoma: primeiro comprei o VL53L8CX; a placa mais comum na China tem **33,4 × 10,2 mm** e não cabe na carcaça do rosto (`face_part`);
para encurtar, troquei para o L7CX (26 mm), mas o firmware reportava erro e encerrava logo ao iniciar. As duas placas foram compras perdidas.
Causa: o L7CX é **outro chip**, de campo de visão amplo de 90°, e o revision ID não confere. O firmware `tof` oficial só reconhece dois, `0x02` (L5CX)
e `0x0C` (L8CX); qualquer outro reporta `neither a VL53L5CX nor a VL53L8CX` e encerra:
o firmware só compila esses dois drivers ULD, não é questão de contornar mudando um ID.
→ Compre o **VL53L5CX (módulo VL53L5X V2)**: o firmware reconhece, **a distância entre furos de 20 mm bate exatamente com a peça impressa** (um colega mediu na peça impressa, furos a 20 mm;
a placa L8CX tem 28 mm e simplesmente não monta), a placa também é a menor (**15,8 × 10 mm** de corpo / 24,7 mm com as orelhas de fixação),
e ainda é 25 yuans mais barata. **A ordem de escolha é: primeiro ver se o firmware reconhece o chip (só L5CX / L8CX), depois ver se a placa cabe**;
escolher primeiro pelo tamanho, ao contrário, foi o que deu este resultado. O chip L8CX em si não tem problema, o problema é aquela placa ser comprida demais;
se for possível achar uma placa L8CX curta, ela também serve; a distância entre furos e a posição da lente devem ser medidas na peça real.
A comparação dos tamanhos dos três tipos de placa está na [lista de compras de eletrônica](docs/电控采购清单.md#4-medição-de-distância-tof--vl53l5cx-ou-vl53l8cx-8multizona).

## Projeto de placa / fabricação de PCB

**O "substituir" na página de pedido da LCSC não grava de volta no projeto**
Clicar em "substituir" na página de pedido para trocar o número de peça vale só para aquele pedido. O componente no projeto do EasyEDA continua com o número antigo, **na próxima exportação da BOM volta tudo ao que era** e reaparece o aviso "biblioteca privada 0".
→ Troque o componente dentro do projeto do EasyEDA (apague e recoloque na mesma coordenada); não troque só na página de pedido.

**Oscilador ativo e cristal passivo em 3225 de quatro pinos são idênticos na aparência**
Nos cristais passivos, os pinos 2 e 4 são a mesma tampa metálica, curto-circuitados internamente. O X1 desta placa foi desenhado como ativo (2=GND, 4=VDD); ao soldar um passivo, **assim que se liga há curto de 3,3 V para o terra**. Na busca da LCSC por "3225", a maioria é de passivos, e o `C13738` (biblioteca básica, sem taxa de troca de peça) é o mais fácil de clicar por engano.
→ Só aceite os que têm na etiqueta "oscilador ativo / OSC". Esta placa usa o `C5917307`.

**O C387369 da 星通时频 não existe no estoque de peças SMT da LCSC**
Na hora do pedido foi classificado em "componentes que usam estoque privado", com biblioteca privada 0.
→ Troque pelo `C5917307` (雅晶鑫, 5 mA, mesmo encapsulamento).

**Depois de adicionar componentes, é preciso reexportar Gerber / BOM / coordenadas**
Depois de alterar o esquemático (por exemplo, adicionando J4/J5), os três arquivos mudam. Fabricar a placa com o Gerber antigo resulta em uma placa sem os furos dos dois conectores.
→ A cada alteração, exporte o conjunto completo, com data e hora no nome do arquivo, e use sempre o mais recente.

**Os conectores PH2.0 escolhidos para J4/J5 têm o passo certo, mas o corpo não combina com o plugue do cabo Feetech e não encaixa**
O cabo do Feetech HD-1910 tem plugue AMP2.0-3P, o passo de 2,0 mm está certo, mas o formato do plugue não combina com o corpo do conector JST PH (`B3B-PH-K-S`). Na revisão alguém já havia avisado que "o conector da placa não foi validado com a peça real", e de fato.
→ Primeira placa: remova o corpo plástico do conector, deixando só os pinos; assim encaixa e funciona. v2: use o cabo Feetech real para casar com o conector (peça à Feetech o modelo do conector da placa, ou compre vários conectores 2,0 mm 3P e teste o encaixe), e **encaixe fisicamente uma vez antes de enviar a placa para fabricação**.
→ Acréscimo (2026-10-13): a especificação da Feetech só informa `AMP2.0-3P` para a ponta do cabo; o modelo do lado da placa não é público e também não achamos na internet nenhum código horizontal validado; outros projetos de réplica escrevem simplesmente "PH2.0", também sem teste real. Mas no desenho dimensional da Feetech, **o fundo do corpo do servo tem dois conectores do mesmo tipo**, o que mostra que a própria Feetech usa o conector de placa correspondente: o mais rápido é perguntar diretamente à Feetech o modelo, se dá para comprar avulso e se existe versão horizontal.

**Caracteres chineses no nome do anexo do GitHub Release são removidos**
Ao enviar `SolidWorks图纸.zip`, ele foi salvo como `SolidWorks.zip`. O link de download escrito no README não bate.
→ Use nomes em inglês nos anexos do Release.

## Ligação com fio solto (sem imprimir o HAT)

> A ligação completa está em [sem HAT](docs/不打HAT.md); aqui só ficam os pontos que mordem.

**A alimentação lógica da placa adaptadora só pode vir de 3,3 V**
A placa adaptadora half-duplex tem um VCC do lado do MCU. Se usar 5 V, o TX dela injeta nível de 5 V no pino RX de 3,3 V do controlador principal.
→ Tire do pino 1 (3,3 V) dos 40 pinos. O ToF tira do pino 17, assim os dois não competem.

**Injetar 5 V nos 40 pinos não tem proteção**
Alimentar 5 V pelos pinos 2/4 contorna a proteção de entrada USB da própria placa. **Se ligar invertido, queima a placa na hora.**
→ Antes de encaixar, meça a polaridade e a tensão da saída do módulo step-down.

**Não use fios dupont no tronco de alimentação dos servos**
Os 15 servos têm pico de vários amperes, e o dupont 24–28 AWG suporta só cerca de 1 A, esquenta e chega a derreter a isolação.
→ No tronco, use fio de silicone 18–20 AWG.

**No trecho da bateria até os servos é preciso colocar fusível e chave em série**
Curto-circuito em bateria de lítio solta fogo. O caminho do HAT oficial tem termistor + marcação "3A max"; a solução com fio solto, ligada direto, não tem nada disso.
→ Coloque em série um fusível de 5 A + chave de alimentação.

**Não há sinal de detecção de desligamento**
O LM5050-1 do HAT dá ao controlador principal um sinal de desligamento; a solução com fio solto não tem. Toda queda de energia é um desligamento brusco, **o que mais machuca o microSD**.
→ Primeiro rode `make shutdown` ou use o gesto de desligar do controle, espere o sistema encerrar completamente e só então corte a energia.

## Servos / calibração

**Software de depuração Feetech FD: instale primeiro o driver, use a versão mais recente, baudrate 1 Mbps**
Três sintomas: ao conectar a URT-2 nenhum servo é encontrado; depois de instalar o driver conecta, mas o modelo do servo é lido como `unknown`; ou conecta e não encontra nada na varredura.
Causas: ① o chip conversor USB-serial da URT-2 precisa de driver; se não há porta COM no gerenciador de dispositivos, é porque não foi instalado; ② a versão do FD é antiga, a tabela de modelos não tem o modelo customizado HD-1910, e o que não é reconhecido aparece como unknown, **mas a leitura e a escrita de registradores funcionam normalmente**; ③ o baudrate de fábrica do HD-1910 é 1 Mbps (registrador 6 = 0), e se o baudrate no FD não for 1000000 a varredura não encontra nada.
→ Ordem: instalar o driver → confirmar no gerenciador de dispositivos que existe porta COM → baudrate 1000000 no FD → usar o FD mais recente do [site da Feetech](http://doc.feetech.cn/). O modelo mostrado como unknown pode ser ignorado, não pense que o servo está com defeito.

**O sentido da contagem de posição do HD-1910 é oposto ao do XL330 oficial, nos 15 servos**
Sintoma: ao arrastar o controle deslizante, o modelo 3D se move ao contrário do real; ao enviar os ângulos da postura oficial em pé, as pernas dobram no sentido oposto.
Causa: o sentido em que a leitura do HD-1910 aumenta é oposto ao do XL330, e a montagem mecânica copia a oficial, então todas as juntas ficam invertidas uma vez, é uma inversão geral, não alguns poucos servos montados ao contrário.
→ Os 15 têm direção −1: [`tools/servo-web/directions.json`](tools/servo-web/directions.json); no robotd é `[bus.feetech] directions`. Os botões ± ao lado de cada servo na página web foram conferidos um a um.

**O HD-1910 não aceita calibração de ponto médio do tipo "escrever 128 na chave de torque"**
Sintoma: a tabela de memória diz explicitamente "escrever 128: calibra a posição atual qualquer como 2048"; seguindo isso o servo responde "sucesso", mas nenhum registrador de offset (31) muda. Se o código em seguida escrever 2048 como posição alvo, a junta é puxada de volta ao zero antigo. Em 2026-09-20 testamos em 4 rodadas com os 15 servos, com a trava liberada e o torque desligado, e o resultado foi o mesmo.
Causa: o firmware 3.46 não suporta isso. A tabela de suporte da seção 4.9 do manual de protocolo diz: SMS ≤2.54 e STS ≥3.10 suportam escrever 128, **HLS ≥3.43 não suporta**, só suporta 0x0B; o comportamento do HD-1910 é coerente com a linha HLS.
→ Use o **comando de calibração de posição 0x0B** (sem parâmetro = calibra para 2048, com parâmetro = calibra para a leitura indicada). Depois de calibrar, sempre releia a posição e o offset para confirmar, não confie no "sucesso" da resposta: a Feetech responde sucesso a muitas operações não suportadas.

**Ao calibrar, não espere com o torque desligado**
Sintoma: depois de desligar o torque e esperar algumas dezenas de milissegundos para ler a posição, a leitura do pescoço (30) caiu 80 passos (7°), e o zero calibrado ficou torto.
Causa: assim que o torque é desligado a junta é empurrada para baixo pela gravidade; quanto mais se espera, mais ela cai.
→ Entre desligar o torque e concluir a calibração não faça sleep, alguns milissegundos bastam; depois de calibrar, escreva imediatamente a nova leitura como posição alvo e só então ligue o torque.


**O D (derivativo, amortecimento) do servo está ligado ao tremor ao andar**
Sintoma: em 2026-10-13, com o R17 no padrão P5/D20, metade do balanço do corpo ao andar era tremor acima de 4 Hz (51%), e o ritmo dos passos ficava bagunçado. O cartão novo V164 usa o D=40 de fábrica.
Causa: o modelo de servo BAM usado no treinamento (os parâmetros são os do 1910 M6 publicados pela 陆吾 (Luwu), `kp_fw=5`, ou seja, P=5 no firmware) não tem o termo D de hardware, mas o robô real tem D. Com D=0 (e ao mesmo tempo torque 1000→850), o tremor caiu para 4～8%. Por que o D causa tremor, "o amortecimento come a ação corretiva" é só uma hipótese, não confirmada pelos dados de seguimento.
→ Primeiro ajuste D=0 para eliminar o tremor. Porém, com D=0 o joelho de apoio estica menos, além de aparecerem o balanço do corpo para frente e para trás (cabeceio) e a ponta do pé esquerdo apontando para baixo (que com D=20 não havia); vale testar o valor intermediário D=5～10. Com D=0, quanto maior o P mais balança: P5 balança 56°/s, P4 44°/s, P3 30°/s (simulação 31°/s). Agora usamos P3 / D0 / torque 700, ao custo de levantar menos o pé. Dados no [registro do robô real da noite de 10-13 §5](docs/HD1910-20261013-夜-掉电-舵机D与蹭地.md#5-走路发颤跟舵机的-d-有关).

**O kissqy V164 (imagem de um clique) não escreve D nem limite de torque; alterar os campos P/D/torque no console não adianta**
Sintoma: no cartão novo, alterar P, D e limite de torque em "parâmetros avançados" do console e, depois de energizar, os registradores do servo não mudam.
Causa: o V164 só escreve o P combinado no pacote do modelo (5, que o kissqy chama de "contrato de implantação"); o D do registrador 51 e o limite de torque do registrador 48 ficam nos valores de fábrica do servo (D=40, 1000), um projeto deliberado dele (o documento de projeto dele diz "manter o valor atual do dispositivo"); no R17 o caminho dos "parâmetros de teste" foi removido. O EEPROM de fábrica do HD-1910 é P32 / D40 / I0.
→ Para ajustar, use o R17; ou, com o robotd parado e os 15 servos sem carga, escreva na RAM dos servos (volta ao original com a queda de energia; o D-pad direito do controle, "reiniciar servos", também restaura); ou altere o D no EEPROM para 0 (uma única alteração; só vale para o V164 que não escreve D; o R17 escreve o próprio D ao energizar, então precisa ser combinado com o kd nos parâmetros de teste). O valor original dentro do servo antes de energizar está em `robot.busStatus` → `native.hd1910.registers_before_arm`.
**Acréscimo (10-14)**: o console 1.0.164 que acompanha o V164 nunca teve os três campos P / D / torque (quem tem esses três campos é o console antigo 1.0.146 que acompanha o R17; se o console antigo se conecta à placa do V164, as alterações não surtem efeito). Liberamos localmente esses itens do V164 (não testado no robô real, não público), veja [registro de 10-14 de dia §8](docs/HD1910-20261014-白天-仿真找原因与新版放开参数.md#8-新版v164放开-p--d--转矩限制和头腿滤波本地未上机).
**Acréscimo (10-14 à noite)**: o kissqy publicou em 10-14 a V167 / control.43 (console 1.0.167), cuja descrição é "corrigir o tremor do corpo do pato": a cada energização por HOME, escreve D=0 e limite de torque 1000 na RAM dos 15 servos, mantendo P=5 do modelo; esses dois valores são fixos e não podem ser ajustados no console; ao tirar a carga só o P é restaurado, o D fica em 0 até o servo ser desenergizado. Isso coincide com a nossa conclusão da noite de 10-13 (mesma mesa, com D20 o tremor ocupava 51%, com D0 caiu para 4～8%). Atenção: para patos com módulo IMU (BNO085 etc.), não clique no "instalar / atualizar firmware" do console dele: o pacote de instalação traz o robotd próprio dele, que não reconhece o módulo IMU; depois da atualização a IMU não é lida e não dá para energizar (veja, em "Software", o item "Se instalou um robotd modificado por você, não clique em 'instalar / atualizar firmware' no console do kissqy").

**P / D / limite de torque do servo ficam na RAM: são escritos a cada energização, restaurados ao tirar a carga e voltam ao valor de fábrica com a queda de energia**
Sintoma: em 2026-10-14 o usuário perguntou: os valores de P / D / torque definidos no console valem sempre, ou precisam ser reescritos a cada vez? Depois de desenergizar o servo uma vez, ou de apertar o D-pad direito do controle (reiniciar servos), ao ler os registradores o que aparece de novo é o valor de fábrica, D40 / 1000.
Causa: o R17 e a versão ajustável que fizemos sobre o V164, a cada energização por HOME, escrevem limite de torque, P e D na **RAM** do servo (registradores 48～51), anotando o valor original antes de escrever e escrevendo de volta ao tirar a carga; o V164 original só escreve o P na RAM (registrador 50). O EEPROM nunca é tocado. Quando o servo é desenergizado, a RAM é recarregada do EEPROM (o HD-1910 sai de fábrica com P32 / D40 / I0 e limite de torque 1000). Os valores definidos ficam num arquivo na placa (`/etc/robot/feetech-ft5/servo-test-parameters.json`) e são reescritos automaticamente na próxima energização, então definir uma vez vale para sempre, sem precisar redefinir a cada vez.
→ Para confirmar que está valendo, veja `robot.busStatus` → `native.hd1910.servo_parameters` (os valores carregados pelo robotd) e `temporary_gains_applied: true` (escrito e conferido por releitura); `registers_before_arm` é o valor original lido antes de energizar, não o valor que foi definido. Há uma armadilha: **se o robotd foi reiniciado com a carga aplicada** (travamento, restart manual, instalar programa com carga aplicada), o valor original anotado se perde. O robotd do V164 e da versão ajustável, assim que inicia, primeiro tira a carga de todos os servos (o pato desaba na hora, segure-o), e no próximo HOME toma os valores de teste residuais no servo como se fossem os originais; o R17 não tira a carga ao iniciar, só confere se os valores batem com o arquivo (se não baterem, recusa o HOME, veja abaixo "Se outro programa aplicou carga e depois você trocou para o kissqy"). Em ambos os casos, os valores de teste ficam na RAM o tempo todo. Continuar usando esse conjunto de parâmetros não tem efeito; mas depois de voltar ao comportamento da versão original, que só escreve P (apagando o arquivo de parâmetros, ou "restaurar padrão" no console), D e torque ficam parados nos valores de teste. Nesse caso, desenergize o servo uma vez. Detalhes em [registro de 10-14 de dia §8.3, §8.4](docs/HD1910-20261014-白天-仿真找原因与新版放开参数.md#83-舵机参数是怎么生效的写-ram不写-eeprom).

**Em pé no HOME, os dois pés não ficam coplanares na direção lateral: os dois rolls do quadril abrem para fora, e a cada vez é diferente (suposição: empurrados pelo peso)**
Sintoma: calculando a cinemática direta a partir das leituras dos servos, em pé no HOME (ou parado depois de andar) as solas dos dois pés não estão no mesmo plano na direção lateral. Em 2026-10-14 calculamos os 14 segmentos, com diferença de 0,6°～13° em relação ao HOME, diferente em cada segmento. De início suspeitamos que o zero do roll do quadril estivesse errado.
Causa: decompondo junta por junta ([`tools/gait-analysis/home_roll.py`](tools/gait-analysis/home_roll.py)), toda a diferença vem dos dois rolls do quadril esquerdo e direito não terem alcançado o alvo do HOME, sempre com esquerdo + e direito − (as pernas abrem para fora), com tamanho diferente a cada vez (0,2°～6,9°). Pela geometria da simulação, a força do apoio no chão atua cerca de 23 mm para fora do eixo do roll do quadril, o que empurra a perna para fora, parecendo ser empurrada pelo peso (suposição; a relação entre quanto desvia e o P não aparece nos dados). Na simulação, a política em pé também tem erro na mesma direção (esquerdo +1,6°, direito −1,8°), e no robô real a maior parte está na mesma ordem de grandeza.
→ A parte que muda a cada vez não é o zero, não altere o zero por causa dela. Mas saiba: esse método compara "leitura − alvo", os dois estão no mesmo ponto zero, então **ele não consegue ver se o próprio zero está deslocado**. No modelo de simulação em pé no HOME, os dois pés já têm a borda externa cerca de 2,3 mm mais baixa; abrir um pouco para fora até achata, abrir demais deixa a borda interna mais baixa; para saber de que lado o pato real levanta, olhe em pé no HOME, de frente, rente ao tampo da mesa, contra a luz; vale o objeto real. Na manhã de 10-14 dissemos de boca que "a borda externa levanta", e em 12 dos 14 segmentos isso era exatamente o contrário; vale esta entrada. Detalhes em [registro de 10-14 de dia §7](docs/HD1910-20261014-白天-仿真找原因与新版放开参数.md#7-站-home-两只脚左右方向不共面两个髋横滚往外劈每次不一样).

**O servo da boca esquenta: fica sempre empurrando a posição fechada e está encostado na placa principal (explicação do kissqy)**
Sintoma: o servo da boca está quente ao toque. Em nossa medição da noite de 2026-10-12, com o pato em pé, o servo da boca ficava a 60～70°C.
Causa: o kissqy explicou no grupo: a posição da boca é fixada em −5° (posição fechada), e depois de fechada ainda continua fazendo força, sempre aplicando esforço; a boca também é o que fica mais perto da placa principal, sendo aquecida pelo calor dela. Ele disse que "mordendo o tempo todo fica só uns 40 graus", e que não é defeito do servo. A temperatura que ele cita é menor que a que medimos, e não investigamos o motivo.
→ Não se apresse em trocar o servo. Para o resfriamento da placa principal, veja abaixo "A placa principal dentro do corpo não tem canal de ar". Se a posição fechada da boca deve recuar um pouco, sem empurrar até o fim, ainda não testamos.

**Instalar o R17 do kissqy faz o zero da unidade de amostra dele ser tomado como a sua calibração**
Sintoma: na primeira instalação do R17, em 2026-10-12, esta máquina não tinha arquivo de calibração; depois da instalação, no `hd1910-calibration.toml` as 15 juntas estavam "calibradas" e o status mostrava "pronto para movimento". Mas os zeros iam de 1372 a 2176, com direções positivas e negativas (zero da cabeça, ID 33, 1599), sem relação com a nossa máquina: nós calibramos com o servo-web, os zeros são todos 2048 e as direções todas −1.
Causa: o script de instalação dele, quando a máquina não tem calibração própria, completa com a calibração da unidade de amostra que vem no pacote e marca como calibrado. A documentação dele também diz "a calibração do pacote é referência da unidade de amostra, cada máquina precisa ser conferida", mas a instalação não barra.
→ Depois de instalar, abra primeiro `/etc/robot/feetech-ft5/hd1910-calibration.toml`, troque pelos seus zeros e direções e, pela fórmula `ângulo = (leitura − zero) × direção × 2π/4096` (a mesma do servo-web), calcule os ângulos de cada junta; só depois de bater com a postura real é que se pode energizar. Antes de bater, não clique em HOME.

**A imagem de um clique R1 do kissqy também vem com a calibração da unidade de amostra dele pré-instalada, e a IMU marcada como "confirmada"**
Sintoma: ao desmontar a imagem dele em 2026-10-12, os zeros em `hd1910-calibration.toml` são do pato dele (2281, 2176……), as direções todas −1, `imu_mount_verified = true`; só `motion_enabled = false` impede.
Causa: a imagem foi feita a partir da unidade de amostra dele. A IMU "confirmada" refere-se à direção de montagem da plaquinha de barramento dele; ao trocar de pato ou de tipo de IMU, deixa de valer.
→ Depois de gravar, primeiro troque pelos seus zeros e direções conforme o item anterior, reconfirme a direção de montagem da IMU e só então mexa no HOME e na chave de movimento. Detalhes em [análise da imagem R1 do kissqy](docs/HD1910-20261012-kissqy镜像R1分析.md).

## Placa principal / HAT / câmera

**Confira a superfície de contato nas duas pontas do flat da câmera; estar encaixado não significa estar ligado certo**
Sintoma: a Radxa Camera 8M219 (IMX219) não lia o chip nem no Armbian nem no B1 oficial, reportando `Reading register 100 from 10 failed` e `Error -5`; em 2026-09-28 o usuário percebeu que o flat podia estar com a face invertida e, depois do ajuste, leu `Model ID 0x0219` e capturou com sucesso 40 quadros de 1920×1080.
Causa: o defeito desapareceu depois de ajustar a direção / o contato do flat; só pelo fato de o conector estar inserido ou pela cor do flat não é possível confirmar que os contatos conduzem.
→ **Faça o desligamento normal, corte toda a alimentação e então confira se os contatos metálicos expostos das duas pontas estão alinhados com as lâminas metálicas dentro do soquete, insira reto e trave.** A ZERO 3W com a Radxa 8M219 usa um flat **22 pin / 0,5 mm → 15 pin / 1,0 mm, contatos na mesma face**; "mesma face" quer dizer que, ao ficar naturalmente plano, as áreas de contato expostas das duas pontas ficam do mesmo lado, e não as trilhas de cobre visíveis por baixo da película.

*Referência de ligação fornecida pelo usuário: à esquerda vê-se a lente, à direita o verso da placa principal, com as marcações Radxa / UKCA. Depois de conferir a orientação relativa geral, ainda é preciso verificar os contatos dentro de cada soquete; em módulos diferentes, não encaixe só pela orientação da lente ou pela face com texto do flat. Esta imagem serve de lembrete de ligação, não é um quadro desta captura.*

**Ver `/dev/video0` não significa que a câmera foi reconhecida**
Sintoma: com a câmera sem responder, a placa ainda tem `/dev/media0` e `/dev/video0..9`.
Causa: esses podem ser apenas nós do lado receptor do ISP Rockchip, sem o sensor vinculado.
→ Confirme em sequência o ID do chip, o vínculo do driver `imx219`, a entidade do sensor em `media-ctl -p` e, por fim, capture quadros de verdade; [comandos completos e resultados desta vez](tools/radxa/摄像头调试记录-20260928.md).

**Os dois conectores Type-C não devem ser adivinhados como "um para alimentar, outro para o computador"**
Sintoma: ligou-se o computador à porta USB 3.0 Host, esperando que aparecesse a porta serial USB da placa principal.
Causa: `5V IN / USB_OTG` é que é a porta de alimentação e também de gadget USB 2.0; o USB 3.0 Host é a porta para periféricos como URT-2 e pen drive; se aparece COM depende ainda de o sistema ter configurado a serial gadget.
→ **Com o HAT alimentado, depure por Wi-Fi + SSH**; no V1.12 o 5V dos 40 pinos está na mesma rede que o VBUS do OTG, então não se pode introduzir pelo cabo de dados USB comum do computador uma segunda fonte de 5V. Para trocar para alimentação por USB, primeiro desligue e desconecte a entrada do HAT. Os 7,4V só podem entrar pela entrada correspondente do HAT, nunca direto nos 5V da placa principal nem no USB-C; veja as [instruções de uso da imagem](tools/radxa/镜像使用说明.md#3-primeira-inicialização).

**O LED verde piscando duas vezes pode ser um batimento normal, não é um código de falha isolado**
Sintoma: no B1 oficial desta vez o LED verde piscava duas vezes, mas Wi-Fi, SSH e câmera estavam todos normais.
Causa: a configuração do LED é `heartbeat`; antes, quando o boot falhava, também já se viu piscar duas vezes, e não se pode tomar o fenômeno concomitante da época como diagnóstico geral.
→ Combine rede, SSH e log de boot para julgar se o sistema subiu; não regrave o cartão só pelo efeito do LED.

**Ao trocar para a imagem oficial como comparação, a ligação também mudou, então não dá para atribuir só à imagem**
Sintoma: o B1 oficial também no início não lia a câmera, só gerou imagem depois de ajustar o flat.
Causa: imagem e ligação não foram retestadas por completo nas mesmas condições; desta vez só se pode confirmar que, na configuração oficial, o reconhecimento da câmera e a captura de curta duração passaram.
→ Mantenha a ligação que deu certo e, conforme necessário, retestar o Armbian original; não declare diretamente que a imagem original está com defeito, nem tome o teste curto de 40 quadros como 30 fps, estabilidade de longo prazo ou aceitação de todas as funções do HAT.


**Placa principal reduzindo frequência por superaquecimento: o serviço web, sempre residente, ocupa um núcleo inteiro e atrasa o ritmo de controle**
Sintoma: em 2026-10-11, ao rodar a política, o período de controle passou de 20 ms para 25 ms, com a leitura de sensores chegando a 20 ms no pior caso; a CPU da placa principal em 84–87°C, com `scaling_max_freq` reduzido ao nível mais baixo, 408 MHz (o máximo é 1800).
Causa: com o `servo-web/server.py` residente, o top mostra um núcleo inteiro ocupado (100%), e a placa principal, instalada dentro do corpo, não dissipa calor; o RK3566 reduz a frequência aos 85°C.
→ Antes de rodar a política, pare o serviço web (`systemctl stop microduck-servo-web`), abra a carcaça da placa principal ou adicione uma ventoinha; antes de rodar, dê uma olhada em `/sys/class/thermal/thermal_zone0/temp` e `/sys/devices/system/cpu/cpufreq/policy0/scaling_max_freq`. Ainda não investigamos por que a página web ocupa toda a CPU.

**A placa principal trava um ou dois minutos depois de ligar, com o LED verde fixo sem piscar**
Sintoma: em 2026-10-11, depois de ligar o SSH conectava, cerca de 2 minutos depois sumia da rede, nem o roteador a encontrava, e o LED verde passava de piscando a fixo. Depois de desligar e reiniciar ficou normal, e não voltou a ocorrer durante o resto da noite.
Causa: indefinida. O LED verde fixo indica que o heartbeat do kernel parou (travamento), não que o Wi-Fi caiu. O log daquele boot não foi gravado no cartão, não dá para investigar. Na ocasião usava-se uma fonte ajustável de 7,4 V.
→ Quando ocorrer de novo, primeiro anote a tensão e a corrente do medidor da fonte e só então desligue e reinicie; não fique ligando e desligando repetidamente.

**Sem câmera e ToF conectados, o mediad e o tofd oficiais ficam reiniciando sem parar e esquentam a placa principal**
Sintoma: em 2026-10-12, depois de instalar o oficial 0.15.1, a placa principal ficou em 89–90°C, com a CPU travada no nível mais baixo, 408 MHz. No top, o `gst-plugin-scanner` do mediad ocupava um núcleo inteiro (99,5%), e o tofd também reiniciava sem parar.
Causa: sem câmera conectada, o serviço de câmera trava assim que inicia, o systemd o levanta de novo sem parar, e a cada vez é preciso varrer de novo todos os plugins do GStreamer; o tofd, sem encontrar o sensor de distância, faz o mesmo. Usuários no grupo também disseram que desligando os serviços sem uso a temperatura cai.
→ Se não há esses dois componentes, rode `sudo systemctl disable --now mediad tofd`, e quando forem conectados depois, `enable --now`. Depois de desligar, em 2 minutos caiu para 85°C, mas ainda está na linha de redução de frequência, e ainda é preciso adicionar dissipação (veja o próximo item).

**A placa principal dentro do corpo não tem canal de ar; mesmo com os serviços desligados chega a 92°C**
Sintoma: depois de desligar mediad e tofd, rodando só o robotd, com o pato em pé, a temperatura voltou a subir lentamente até 92,5°C, com a CPU o tempo todo em 408 MHz. O timeout na leitura de retorno ao energizar é causado pela CPU lenta demais; o joystick web sem resposta também fica pior por causa disso (a causa raiz não é só superaquecimento, veja [Software](#software)). Na noite de 2026-10-12, com todos os serviços desligados e também retirada a reconexão SSH, ao rodar o modelo, em cerca de 10 minutos a CPU ainda chegava a 85°C e caía para 408～600 MHz (o robotd rodando o modelo ocupa 30%～46% de um núcleo).
Causa: a placa principal dentro do corpo não tem dissipador nem caminho de entrada e saída de ar. O RK3566 reduz a frequência aos 85°C, e depois de cair ao nível mais baixo todos os programas ficam lentos.
→ Primeiro faça alguns furos na carcaça da cabeça ou do corpo, o mais simples, e dissipa parte do calor. Para realmente dissipar, a chave é o **canal de ar**: ter um lugar por onde o ar entre e outro por onde saia; a ventoinha não precisa estar colada à placa principal. Antes de ir para o robô, olhe `/sys/class/thermal/thermal_zone0/temp` e `/sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq`; se a frequência estiver em 408000, está reduzindo.

**O robô completo perde energia e reinicia ao andar ou levantar: é a alimentação, não o software**
Sintoma: em 2026-10-13, tanto o cartão novo quanto o antigo, ao andar ou levantar, desligavam e reiniciavam de repente, com a gravação de vídeo e o log do sistema interrompidos ao mesmo tempo, sem processo de desligamento. O cartão novo (D=40) caiu 13 segundos depois de o modelo assumir, e no último instante o servo leu cerca de 3,9 V; o cartão antigo (D=20) aguentou 42 segundos, com uma queda e levantada no meio, e cerca de 11 segundos depois de levantar perdeu energia, com o joystick em 0 na hora.
Causa: o impulso de corrente de mais de uma dezena de servos fazendo força ao mesmo tempo, que a fonte e os fios não suportam; o 5 V da placa principal é obtido pelo HAT por step-down da mesma linha de energia, e cai junto. Quanto maior o D, mais frequentes as correções do modelo e talvez mais impulsos (o cartão novo ainda estava com o som ligado, comparar uma vez contra a outra não permite conclusão). A tensão reportada pelo robotd vem a cada 0,5～1 segundo, sem ver quedas de dezenas de milissegundos.
→ Use bateria ou fonte de alta corrente (10 A), com fios de 16～18 AWG, o mais curtos possível, conectores XT30/XT60, e em paralelo na entrada um capacitor de 1000～2200 µF. Para separar se é a fonte principal ou o trecho do HAT para a placa principal: alimente o USB-C da placa principal separadamente por um power bank e ande de novo. O repositório do kissqy chegou a escrever "margem insuficiente do LM5050 causa reinício", mas ele apagou em 10-12 (correção do autor), não cite. Detalhes em [registro do robô real da noite de 10-13 §2](docs/HD1910-20261013-夜-掉电-舵机D与蹭地.md#2-整机掉电是供电不是软件).
**Acréscimo (10-15 à noite)**: o cartão novo reiniciou de novo o robô completo (19:31:42); desta vez o pato estava parado em pé no lugar, em modo walk, sem empurrar o joystick, e um instante antes a bateria estava em 7,59 V e a CPU em 78°C, com o fim do arquivo de gravação sendo uma sequência de bytes nulos. Não foi numa ação grande, então "apenas impulso de esforço" pode não se sustentar; a causa ainda não está definida, e quando a fonte de 10 A chegar faremos o teste de comparação. Veja [registro de 10-15 §6.2](docs/HD1910-20261015-IMU乱跳根因与陀螺融合上机.md#62-整机重启193142).

**Ao ligar um módulo IMU externo ao J5 do HAT, primeiro veja quais chips da placa já ocupam endereços**
Sintoma: o J5 (pinos 3/5 dos 40 pinos, I2C3) já tem chips da própria placa nessa linha: as duas versões têm o áudio aic3104 (0x18); a versão C1 (a que temos em mãos) tem ainda o BMI088, acelerômetro 0x19, giroscópio 0x68; a versão D1 (a mais recente oficial) trocou para LSM6DSV16X, 0x6A.
Causa: o I²C distingue dispositivos por endereço, e dois chips no mesmo endereço brigam entre si e nenhum é lido certo. O BNO085 externo (0x4A/0x4B) não conflita em nenhuma das duas versões; um LSM6DSV16X externo na D1, se também usar 0x6A, bate com o da placa.
→ Antes de ligar, rode `i2cdetect -y 3` para ver os endereços ocupados; o LSM6DSV16X externo na D1 usa 0x6B (SA0 em alto), e no robotd escreva explicitamente `i2c_address = 0x6B`. A IMU da placa está na cabeça, só serve como IMU da cabeça, e o módulo externo deve ser instalado no tronco. Se não quiser ocupar o J5, dá para mudar o J6 para I2C4 (retirar R18/R19, curto-circuitar R16/R17). A comparação pad a pad entre C1/D1 está em [análise da imagem R1 do kissqy §9](docs/HD1910-20261012-kissqy镜像R1分析.md#9-hat-上接-imu-模块c1旧版咱们手上这块和-d1官方最新版对照).

**Mau contato no módulo IMU: o robotd julga a IMU desatualizada e o pato tira a carga direto**
Sintoma: na noite de 2026-10-12 o pato amoleceu de repente; ao apertar Start respondeu `nothing to bring up state=Limp`, o `robotctl health` mostrou `orientation frozen`, e o log do robotd `trunk IMU reader fault … No such device or address (os error 6)`.
Causa: o BNO085 parou de responder no I²C (ninguém responde no endereço). Nas 77 desconexões, a tensão dos servos estava em 7,3～7,5 V, não é alimentação; a maioria ocorreu enquanto balançava ao andar, e algumas em repouso total, o que mostra que algum ponto já está solto. O robotd trata a IMU sem atualizar como falha de leitura, e depois de falhas consecutivas tira a carga por proteção, o que em si está certo; quando a IMU volta, o driver a reconhece sozinho de novo.
→ Solde bem o fio ou use conector com trava, fixe as duas pontas com cola quente e deixe folga na passagem pelo pescoço; depois de soldar, reverifique uma vez com a calibração do zero abaixo. [`imu_fault_ctx.py`](tools/radxa/onboard-analysis/) consegue associar cada desconexão ao que estava acontecendo e à tensão naquele momento.

## Software

**Com o Clash em modo TUN no computador, ping, SSH e web não conseguem alcançar a placa principal**
Sintoma: em 2026-10-11 a placa principal estava claramente online (a porta 22 aparecia aberta na varredura), mas o ping do computador não passava, o SSH reportava `Error reading SSH protocol banner` e o navegador abrindo `http://192.168.0.102:8080` dava 502.
Causa: a placa de rede virtual TUN do Clash Verge (Meta) assume todas as rotas, inclusive a rede local (`Find-NetRoute` mostra a rota via Meta), e a conexão com a placa principal é interceptada por ela.
→ Desligue o TUN temporariamente, ou no Clash defina `192.168.0.0/16` como conexão direta. Quando não quiser mexer no Clash, no programa vincule a conexão ao endereço local da placa de rede cabeada (Python `socket.bind(('192.168.0.100', 0))` e depois conecte à placa principal) e dá para contornar; a página web pode ser acessada com um redirecionamento de porta local, ou abrindo pelo celular.

**Na imagem de um clique do kissqy, o G50 Pro pareia com sucesso e é desconectado em poucos segundos**
Sintoma: em 2026-10-13, cartão novo (imagem R1 do kissqy), com o controle na posição S, o `bluetoothctl pair` mostra sucesso e logo desconecta, e o padd não lê. No cartão antigo, o mesmo controle não tinha problema.
Causa: neste cartão o Bluetooth, ao iniciar, não é "bondable" (motivo não esclarecido); o pareamento volta No Bonding, a chave não é guardada, e o BlueZ por padrão tem `ClassicBondedOnly=true`, aceitando só HID já vinculado, e portanto recusa. O setup-board oficial define propositalmente o `UserspaceHID` do `/etc/bluetooth/input.conf` como false (o controle vai pelo kernel, economizando cerca de 16% de CPU de um núcleo; na placa oficial o pareamento não tem problema); se ele participou não foi verificado.
→ Antes de parear, `btmgmt bondable on`, depois `pair` → `trust` → imediatamente `connect`; ao ter sucesso, é possível ver `Nintendo Switch Pro Controller` e `hid_nintendo`. Na ocasião também mudamos o `input.conf` para `UserspaceHID=true`, `ClassicBondedOnly=false`, várias coisas de uma vez, **só deu certo uma vez, e nas duas seguintes não pareou**; o `UserspaceHID=true` consome mais CPU, da próxima vez tente primeiro só com bondable.
**Acréscimo (10-15 à noite, mesmo cartão)**: com `pair`, `trust` e `connect` digitados como três comandos separados, o pareamento teve sucesso, mas a conexão foi recusada pelo controle (`control_connect_cb() … Permission denied (13)`); apertando o HOME do controle para ele reconectar, conectou, caiu após 10 segundos, e o controle também não apareceu no sistema. Primeiro `btmgmt bondable on`, `btmgmt connectable on`, apague o registro antigo com `bluetoothctl remove <endereço do controle>` e depois faça tudo de uma vez na **mesma** sessão do `bluetoothctl` (`agent NoInputNoOutput` → `default-agent` → `scan on` → esperar o controle aparecer → `pair` → `trust` → `connect` imediatamente) e funcionou; o log do padd `pad connected — driving pad=Nintendo Switch Pro Controller`, e o Wi-Fi também não caiu. Desta vez o `input.conf` ainda estava como alterado em 10-13 (`UserspaceHID=true`, `ClassicBondedOnly=false`), sem verificar separadamente qual item é indispensável.

**O G50 Pro só lembra do último cartão pareado; ao trocar de cartão é preciso parear de novo**
Sintoma: depois de o controle ser pareado com o cartão novo, ao voltar ao cartão antigo o controle não conecta nele.
Causa: o controle guarda só a chave do último pareamento, e o cartão antigo ainda guarda a anterior, que não confere.
→ A cada troca de cartão, refaça o pareamento no cartão atual (o procedimento do item anterior).

**O IP fixo usado pelo pato foi ocupado por outro dispositivo da rede local, e o computador ora conecta, ora não**
Sintoma: em 2026-10-13 o cartão antigo usava o estático 192.168.0.102, e ao mesmo tempo outro dispositivo da rede local (pelo endereço da placa de rede, parece um celular) também recebeu o .102, e a conexão do computador ao pato oscilava.
Causa: o DHCP do roteador não sabe que o pato ocupou manualmente esse endereço, e o entregou a outro.
→ No roteador, faça uma "atribuição de endereço estático" para o pato (vinculada ao MAC), ou defina o IP fixo do pato fora da faixa do DHCP. Solução provisória: primeiro desligue o Wi-Fi do dispositivo que ocupou o endereço, ou, no computador, como administrador, vincule estaticamente esse IP ao MAC do pato (`netsh interface ip add neighbors`, perde efeito ao reiniciar o computador).

**Depois de uma queda de energia do robô completo não há log nenhum: o log do Armbian fica na memória**
Sintoma: depois da queda e reinício, ao olhar o `journalctl` só há o desta inicialização; os últimos segundos da nossa gravação também não foram escritos no cartão. A placa principal não tem RTC, o relógio volta atrás a cada boot, e nem pelo horário se descobre qual é o arquivo.
Causa: o Armbian por padrão põe o log em zram (memória), sem gravar em disco, de propósito, para proteger o cartão SD; o buffer de arquivo do Python só grava a cada alguns segundos.
→ Ative um serviço para a gravação e outro para o log do sistema, **com fsync a cada segundo**, e o nome do arquivo com o número do boot (os 6 primeiros caracteres de `/proc/sys/kernel/random/boot_id`). Os scripts são `duck_rec.py`, `duck_journal.py` e os dois services em [`tools/radxa/onboard-analysis/`](tools/radxa/onboard-analysis/). Não desligue o zram (veja abaixo "Não desligue o armbian-zram-config").

**O Armbian vem de fábrica com `overlay_prefix=rk35xx`, mas os overlays do RK3566 se chamam `rk3568-*`**
Com o prefixo errado, o carregador não acha nada e falha em silêncio; a placa inicia normalmente, **mas não há `/dev/ttyS2`**. Você vai achar que o fio foi ligado errado. Depois de um `apt upgrade` que troque o kernel, pode voltar ao estado original.
→ No `/boot/armbianEnv.txt` mude para `overlay_prefix=rk3568`, adicione `overlays=uart2-m0` e reinicie. O `setup-board.sh` oficial faz exatamente isso.

**O console do kernel também usa o ttyS2 por padrão**
A UART2 é a serial de depuração do RK3566, e o Armbian envia o log do kernel para ela, ou seja, para o barramento dos servos.
→ No `extraargs` do `/boot/armbianEnv.txt`, remova `console=ttyS2,1500000`.

**O Armbian por padrão roda um console de login na UART2**
O `agetty` ocupa o `/dev/ttyS2` e o servo não se comunica de jeito nenhum. Mesmo com o fio ligado certo não comunica, e muito provavelmente é isso.
→ `systemctl mask serial-getty@ttyS2` e depois `fuser -v /dev/ttyS2` para confirmar que não há outro processo.

**Não desligue o armbian-zram-config**
O Armbian por padrão põe o log em zram (memória), sem gravar em disco, para proteger o cartão SD. Alguns o desligaram para ver logs com mais facilidade, e o volume de gravação multiplicou várias vezes.
→ Deixe ligado. O `deploy/README.md` oficial diz textualmente: não gravar em disco é um "arranjo intencional", e desligar é "decisão de cada placa, não o padrão".

**Usar os pinos 3/5 no i2c3 faz perder a negociação USB-C PD**
O i2c3 do RK3566 de fábrica roda no pinmux M1 servindo o FUSB302 (USB-C PD). O overlay oficial o move para M0 (pinos 3/5) e desabilita o fusb302.
→ Aceite esse custo: o USB-C continua dando 5 V, só não negocia. O robô é alimentado pela bateria, nada a ver com isso.

**O `wsl --mount` não monta leitor de cartão USB; não conte com ele para gravar arquivos num cartão já gravado**
Ao tentar usar o WSL2 para escrever o preset de primeira inicialização do Armbian, `.not_logged_in_yet`, na partição raiz ext4 do cartão, `wsl --mount \\.\PHYSICALDRIVE2 --partition 1` reporta direto `Wsl/Service/AttachDisk/MountDisk/HCS/ERROR_FILE_NOT_FOUND`. Isso é uma limitação do WSL com discos USB removíveis, sem relação com o cartão estar bem gravado ou não.
→ Faça ao contrário: primeiro coloque o arquivo dentro da imagem e depois grave. No WSL, descompacte o `.img.xz` em disco local (não pode ficar em `/mnt/`, o loop não monta), monte a partição raiz com `mount -o loop,offset=$((32768*512))`, escreva o arquivo e grave o `.img` gerado. O script está em [`tools/radxa/`](tools/radxa/).

**A imagem Armbian testada antes trava na inicialização na Zero 3W V1.12 (versão Wi-Fi AIC8800): é preciso julgar pelo log e pelo disco do sistema**
A Zero 3W fabricada de 2024-11 em diante é a V1.12; gravando a imagem vendor do Armbian 26.2.1 / 26.8.1, o LED tem heartbeat de duas piscadas (o kernel subiu), mas nem chega ao initramfs, o disco do sistema não tem um único byte tocado, e nunca se acha na rede local.
A imagem oficial da Radxa, no mesmo cartão e na mesma placa, subiu de primeira. Depois de excluir item por item (cartão, modo de alta velocidade SDR104, alimentação, device tree, tudo igual), a diferença que resta é só o bootloader:
o Armbian usa para a zero3 o U-Boot mainline 2025.10 + firmware de inicialização de memória v1.21 de 2024-01; a própria Radxa usa o rk U-Boot 2017.09 + DDR v1.23 (2024-09) + BL31 v1.45.
→ Grave o `idbloader.img` / `u-boot.itb` do pacote `u-boot-rk2410` da Radxa nos setores 64 / 16384 do cartão e depois escreva para o Armbian um `/boot/extlinux/extlinux.conf` (o U-Boot da Radxa usa extlinux, não lê boot.scr), sem alterar uma vírgula do kernel e do sistema, e sobe na hora.
O script em [`tools/radxa/`](tools/radxa/) faz o cartão com um clique. Método para localizar esse tipo de problema mesmo sem serial: ler o cartão e ver se a partição raiz foi escrita, e colocar sinal de LED e log de caixa-preta dentro do initramfs.

**Na V1.12J (este lote de 2026-09), trocar só o boot não basta; o device tree também precisa ser trocado**
Sintoma: depois de trocar para o boot da Radxa conforme o item anterior, o Armbian ainda não sobe; a imagem B1 oficial da Radxa sobe. Alguns também encontraram que, em partida a frio com o HDMI conectado, não liga.
Causa: neste lote de placas o Wi-Fi mudou para AIC8800DS2, e o `rk3566-radxa-zero3.dtb` que vem com o Armbian não o reconhece; o da imagem B1 da Radxa reconhece.
→ Pegue o boot e **o DTB, ambos, da imagem B1**, o `fdt` do extlinux aponta para a cópia trazida, e o kernel e o sistema de arquivos raiz ficam do Armbian
(os dois lados têm kernel vendor 6.1, dá para misturar). Um colega do grupo testou e funcionou em 2026-09-20. Depois de trocar o DTB, lembre-se de verificar se `/dev/ttyS2` e a serial USB continuam lá,
pois os overlays são do Armbian e os nós podem não bater. Comandos nas [instruções de uso da imagem](tools/radxa/镜像使用说明.md#6-se-a-sua-placa-não-for-deste-lote).

**Depois de trocar para o boot da Radxa, alterar o `armbianEnv.txt` não surte efeito**
Sintoma: foi adicionado um overlay no `overlays=` do `/boot/armbianEnv.txt` (por exemplo `i2c3-pihat`), e depois de reiniciar o `/dev/i2c-3` continua não existindo; o `setup-board.sh` oficial alterando-o dá o mesmo resultado, enquanto a verificação do próprio script diz que já está configurado.
Causa: o U-Boot da Radxa só lê o `/boot/extlinux/extlinux.conf` e não roda o `boot.scr` do Armbian, e quem lê o `armbianEnv.txt` é justamente o `boot.scr`.
→ O overlay precisa ser escrito na linha `fdtoverlays` do `extlinux.conf`, com o caminho completo do dtbo (`/boot/dtb/rockchip/overlay/rk3568-xxx.dtbo`); confirme que o arquivo existe antes de reiniciar.

**O AIC8800 não suporta GCMP-256; com o modo misto WPA3 ligado no roteador, não conecta**
O AIC8800D80/DS2 da Zero 3W V1.12 só tem CCMP-128. Roteadores domésticos (TP-LINK etc.) vêm por padrão em modo misto WPA2/WPA3, e a metade WPA3 usa GCMP-256, e o handshake falha.
→ No wpa_supplicant force `key_mgmt=WPA-PSK`, `pairwise=CCMP`, `ieee80211w=0` (o script de fazer o cartão já traz), ou mude o roteador para WPA2 puro. Conecta tanto em 5 GHz quanto em 2,4 GHz.

**Ao ligar a placa no computador não aparece serial USB: é preciso o overlay `dwc3-peripheral`**
No device tree da porta OTG da Zero 3W está `dr_mode = otg`; com o kernel vendor do Armbian, ao ligar no computador ele não muda sozinho para modo dispositivo, e mesmo carregando o `g_serial` o computador não enxerga.
→ No extlinux, carregue o `rk3568-dwc3-peripheral.dtbo` (que vem com o Armbian), depois `g_serial` + `serial-getty@ttyGS0`, e ao ligar no computador aparece mais uma porta COM, com login direto como root, salva-vidas em emergência. O script de fazer o cartão já traz.

**Rodando os scripts oficiais na placa, o GitHub não baixa**
`setup-board.sh` / `install.sh` baixam coisas de raw.githubusercontent.com, api.github.com e objects.githubusercontent.com; na China, com conexão direta, praticamente trava (com IPv6 prioritário é pior).
→ No Clash do computador ative "permitir LAN", e no `/etc/environment` da placa escreva `http_proxy=http://IP-do-computador:7890` (no `card.conf` do script de fazer o cartão basta preencher `HTTP_PROXY=`). O apt usa as fontes do Debian, sem precisar de proxy.
Atenção: na instalação oficial, quem chama o gancho de instalação é o updaterd, e o curl dentro do gancho não lê o `/etc/environment`. Em 2026-10-12, ao baixar o ONNX Runtime, a conexão direta deu timeout em 90 segundos; depois de escrever para o root um `/root/.curlrc` (uma linha `proxy = "http://IP-do-computador:7890"`), baixou em dois segundos; depois de instalar, lembre-se de apagar.

**O install.sh oficial só instala a versão mais recente, e o R17 do kissqy precisa da 0.15.1**
Sintoma: o R17 do kissqy é construído sobre o `daemon-v0.15.1` oficial, e o oficial em 10-07 já chegou à 0.16.1, e o `install.sh` sempre instala a mais recente, sem opção para indicar a versão.
Causa: o script faz o updaterd procurar sozinho o latest no GitHub.
→ Primeiro baixe localmente os arquivos de release do `daemon-v0.15.1`, copie o `install.sh`, fixe a tag de release como `daemon-v0.15.1` e, no `updaterd install`, adicione `--from <diretório local>`. A verificação de assinatura é feita normalmente. O script já ajustado está em `Radxa-Zero3W/official-daemon-v0.15.1/scripts/install-local.sh`. Depois de instalar, mude o `auto_apply` do `/etc/robot/updater.toml` para `"off"`, para que ele não se atualize sozinho.

**Se não usa som, não rode a parte de áudio do setup-board.sh oficial, e não rode o migrate-network.sh remotamente**
Sintoma: o passo de áudio do `setup-board.sh` instala por apt o kernel vendor do Armbian e aponta `/boot/Image`, `dtb` e `uInitrd` para o novo kernel; o `migrate-network.sh` muda o Wi-Fi do netplan para o NetworkManager.
Causa: esta placa V1.12 só inicia com o U-Boot da Radxa e o `extlinux.conf`, e trocar o kernel remotamente corre o risco de não ligar mais. Esta etapa serve apenas para habilitar o chip de áudio do HAT, e para andar não se usa som; sem o HAT instalado, menos ainda. Se ao trocar a rede o Wi-Fi cair, não dá para reconectar remotamente.
→ Se não quer som, nenhum dos dois precisa ser rodado: o overlay da serial dos servos e a cessão do console serial já foram resolvidos ao fazer o cartão. Para andar só são necessários os serviços instalados pelo `install.sh` oficial.

**Instalando o R17 do kissqy, sem a placa de som aic3104 no sistema ele trava na configuração de áudio**
Sintoma: o `service.sh upgrade` para em `alsactl store aic3104`, código de saída 19, com a mensagem "instalação incompleta; estágio: audio-setup".
Causa: o script de instalação dele assume que essa placa de som sempre existe. Sem o HAT, ou com o HAT mas sem rodar o passo de áudio do `setup-board.sh` oficial (o caso da primeira máquina em 2026-10-12), o sistema só tem a placa de som HDMI.
→ O nosso branch já corrigiu (sem essa placa de som, pula a configuração de áudio, sem afetar o andar). Ao usar o pacote original dele, dá para primeiro alterar o `voice-setup.py` no pacote e recalcular o `SHA256SUMS`.

**A imagem de um clique R1 do kissqy usa o boot original do Armbian, e a placa V1.12 pode não subir**
Sintoma: em 2026-10-12, ao desmontar a imagem R1 dele, a área de boot é o U-Boot mainline 2025.10 do Armbian + firmware de inicialização de memória v1.21, via `boot.scr`; a nossa primeira máquina (V1.12, AIC8800) travou em setembro justamente nessa combinação.
Causa: a placa dele liga, o que mostra que o lote dele combina com esse boot; não dá para generalizar se todas as V1.12 não funcionam, mas a nossa com certeza não.
→ Use [`tools/radxa/kissqy-r1-v112.sh`](tools/radxa/kissqy-r1-v112.sh) para, na imagem dele, trocar pelo boot da Radxa e escrever o extlinux (o overlay dele é levado como está), sem mexer no resto. Validado offline: a área de boot é idêntica byte a byte ao pacote da Radxa, a tabela de partições não foi tocada, e a partição raiz só mudou nos pontos esperados. **Ainda não testado no robô real**; teste primeiro com um cartão vazio, não grave sobre o cartão em uso. A V1.12J talvez ainda precise trocar o device tree conforme o item anterior.

**A imagem de um clique R1 do kissqy só reconhece a plaquinha de IMU no barramento; módulo IMU não funciona**
Sintoma: o robotd da imagem (control.40) só tem código para ler o ID 200, exigindo que a identidade da plaquinha seja `06 00 00 00 F2` (o firmware FT6 dele), e não tem código para ler IMU por I²C; a configuração de boot também não habilita o I2C4. Um pato com módulos BNO085 ou LSM6DSV16X, ao receber essa imagem, trava em "Feetech ID 200 sem resposta".
Causa: o conjunto dele foi feito para o hardware dele. O suporte a IMU I²C que adicionamos ao robotd (branch `hd1910-trunk-imu-i2c`) foi escrito sobre o código-fonte v146, e o código-fonte do V164 dele ainda não é público.
→ Quem usa módulo IMU deve continuar com o conjunto próprio instalado, v146 + IMU I²C (veja o [registro do robô real de 10-12](docs/HD1910-20261012-kissqy整套上机.md)); quando ele publicar o código-fonte do V164, portamos o patch, ou pedimos que ele o incorpore à imagem.

**O `service.sh init` não consegue enviar HOME enquanto o robotd está rodando**
Sintoma: em modo de movimento, `sudo bash service.sh init` reporta `cannot claim robot IPC socket … another robotd owns this socket`.
Causa: o subcomando `robotd init` exige o lock exclusivo do robotd, e só serve quando o robotd não está rodando. O console dele envia JSON-RPC por `/run/robotd.sock` (uma por linha, `{"jsonrpc":"2.0","id":1,"method":"robot.init","params":{}}`).
→ Use o HOME do console, ou envie você mesmo `robot.init` ao socket. Para habilitar e parar a política use `robot.enable` (`{"on":true}` / `{"on":false}`), e para tirar a carga, `robot.relax`.

**O joystick web não responde ao apertar: quatro camadas de causa empilhadas, não só superaquecimento**
Sintoma: em 2026-10-12 o console do kissqy (R17 v1.0.146) conectou, os dados estavam todos normais, mas clicar em HOME e Start do controle web não fazia nada. O log do console dizia "entrada expirada, não enviada" ou "timed out", e o padd ocasionalmente reportava `Failed to open "/dev/input/event4"`.
Causa: a cada tecla apertada, é aberta uma nova conexão SSH, o webpad é iniciado sob demanda, um controle virtual é criado e se espera o padd reconhecê-lo, e as quatro camadas são lentas. ① O Armbian roda em vão um script de boas-vindas de 3,8 segundos a cada login SSH; ② o console estabelece que, se o canal não abre em 0,4 segundo, é descartado; ③ a partida a frio do webpad mais o padd reconhecer o controle leva 1～2 segundos, e ao clicar e soltar logo, a tecla se perde; ④ o padd tenta abrir antes de o sistema terminar de registrar o novo dispositivo, falha e não tenta de novo (rodar o padd como root dá o mesmo, não é problema de permissão). De madrugada achamos que era só superaquecimento, que apenas deixava cada camada mais lenta.
→ Use o controle físico Bluetooth (próximo item), contornando todo o caminho. Se ainda quiser o controle web, primeiro desligue o script de boas-vindas do SSH (item depois do próximo) e segure a tecla por 1～2 segundos antes de soltar. O kissqy no V164 já mudou o controle web para ir direto pelo robotd. As medições camada por camada estão no [registro do robô real da noite de 10-12](docs/HD1910-20261012-夜-IMU校准与首次迈步.md#1-网页手柄按了没反应四层原因叠在一起).

**雷神 G50 Pro como controle físico: chave S atrás, pareia direto com o pato por Bluetooth**
Sintoma: o receptor 2.4G do controle ligado no computador não serve para o pato: o console web não lê o controle do computador; e o receptor não pode ser ligado à placa principal dentro da cabeça.
Causa: tanto o projeto oficial quanto o do kissqy usam controle Bluetooth pareado direto com a placa principal, lido pelo padd. O X / S / T / D atrás do G50 Pro é seleção de plataforma, não de cabeado ou sem fio; a posição S se apresenta como controle Pro do Switch, com driver já no kernel da placa principal e também suportado pela ferramenta de pareamento oficial.
→ Retire o receptor do computador, chave em S atrás, com o controle desligado segure HOME até o LED piscar rápido; na placa principal `sudo systemctl start configd`, depois `sudo robotctl pad pair`. Se não achar, use o `bluetoothctl` para escanear o endereço do `Pro Controller` e `robotctl pad pair <endereço>`. Depois de pareado, reconecta sozinho. "≡" é Start (o primeiro toque é HOME, o segundo faz o modelo assumir), "⧉" é Select (tira a carga). Na configuração da placa principal o X está ligado à cambalhota para frente, não aperte as teclas de letra à toa.
**Acréscimo (10-21, imagem da réplica 20261021b, terceiro pato): na nossa imagem é preciso a posição X, a S não funciona.** Pareando a posição S na página de controle do Studio: o assistente (o `robotctl pad pair` oficial) informa que pareou, mas o kernel nunca mostra o dispositivo de entrada do controle, o padd não o encontra e o controle desliga sozinho depois de algumas dezenas de segundos; na posição X (Xbox) conecta de imediato, e a parada de emergência e o andar estão normais. A causa ainda não está esclarecida: na ocasião o Bluetooth do pato estava "não bondable, não connectable", e em `/var/lib/bluetooth` também não ficou registro de pareamento (mas no meio clicamos duas vezes em "esquecer", e o sumiço do registro pode ser por isso). Na próxima vez que parear na posição S, capture com `btmon` e investigue.

**O Armbian roda em vão um script de boas-vindas de 3,8 segundos a cada login SSH**
Sintoma: o login SSH é lento; ferramentas que abrem SSH com frequência (o controle e o canal ToF do console do kissqy) dão timeout assim que usadas, e a CPU da placa principal fica ocupada o tempo todo.
Causa: o `pam_motd.so motd=/run/motd.dynamic` em `/etc/pam.d/sshd` faz cada login rodar tudo em `/etc/update-motd.d/`, dentre os quais só o `20-ip-info` leva 2,9 segundos, somando 3,8 segundos.
→ Primeiro faça backup e depois comente essa linha (a linha `pam_motd.so noupdate` fica). Depois da alteração, cada pergunta e resposta via SSH caiu de 3～4 segundos para 0,7 segundo.

**Sem ToF conectado, o console do kissqy reconecta por SSH a cada 5 segundos**
Sintoma: em 10 minutos a placa principal recebeu 112 logins SSH, e cada um ainda rodava o script de boas-vindas do item anterior.
Causa: o tofd está desligado (ToF não conectado), o console falha ao assinar o ToF e tenta indefinidamente, e cada tentativa é um login SSH completo.
→ Se não conecta ToF, não deixe o console assiná-lo; no console do nosso branch foi adicionado `--tofd-socket ""`.

**O Start do controle precisa de dois toques: o primeiro é HOME, só o segundo é o modelo assumindo**
Sintoma: depois de levantar, empurrar o joystick não faz nada, e o log diz `the policy is not driving — press Start on the pad`; às vezes, ao apertar o segundo toque, ele volta mais uma vez ao HOME.
Causa: o primeiro só trava as juntas na postura em pé, e o modelo não é ligado; só no segundo o modelo assume e o joystick passa a funcionar. Antes de assumir, o robotd ainda verifica a postura: cada junta a ≤5° do HOME, inclinação do corpo ≤10°, por 3 quadros seguidos, e se não passar volta de novo ao HOME.
→ Depois de levantar, tire a mão e espere ele se estabilizar sozinho antes de apertar o segundo toque. Se foi recusado, veja qual condição não passou: joelho cedendo, IMU desviada ou corpo torto.

**No preset da primeira inicialização do Armbian, faltando duas variáveis, ele para no prompt esperando alguém digitar**

**No código-fonte do kissqy há dois `padd.service`, e o pacote de instalação instala o de `packaging/`**

**Compilação cruzada do padd falha com erro de build do `libudev-sys`**
O gilrs que o padd usa para ler o controle precisa ligar com o libudev, e a compilação cruzada do `cargo board` não acha o libudev aarch64 (robotd e robotctl não dependem dele, por isso antes não aconteceu).
→ Use o `scripts/cross-sysroot.sh` do próprio repositório, que puxa os pacotes arm64 do Debian e os descompacta num sysroot; na China defina `DUCK_DEBIAN_MIRROR=https://mirrors.ustc.edu.cn/debian`; ao terminar, copie as linhas de `export` que ele imprime para o shell atual e depois `cargo board -p padd`.

**Os números de versão da interface do oficial novo e da versão do kissqy sobem cada um por conta própria; o mesmo número significa coisas diferentes**
Ao portar funções do oficial novo para a base do kissqy, é fácil achar que "versões próximas são compatíveis". O kissqy foi do 37 do oficial 0.15.1 por conta própria até 40, e o oficial foi de 37 até o 41 da 0.17.1, e as interfaces novas de cada lado são diferentes.
→ Ao portar funções, confira uma a uma se as interfaces a chamar existem no robotd do kissqy (desta vez foram conferidos `sit_toggle`, `robot.policies.sitting` e os dois tipos de som); não aplique por inteiro o código do cliente oficial.

**O "corrigir conexão do controle" do novo console do kissqy só reconhece o 盖世小鸡 Nova 2 Lite, e não adianta nada para o G50 Pro**
Sintoma: na noite de 2026-10-13, ao trocar para a versão nova do kissqy (console R17 V164 1.0.164), o 雷神 G50 Pro não conectava; o kissqy sugeriu clicar em "corrigir conexão do controle" no console.

Com outros controles ela recusa direto e não apaga o pareamento do G50 Pro, então não adianta para o G50 Pro. O G50 Pro não conectar no cartão novo tem outra causa, que descobrimos: o Bluetooth "não bondable", o pareamento volta No Bonding (veja acima "Na imagem de um clique do kissqy, o G50 Pro pareia com sucesso e é desconectado em poucos segundos").
→ Para o G50 Pro, pareie manualmente conforme [10-13 noite §1.2](docs/HD1910-20261013-夜-掉电-舵机D与蹭地.md#12-g50-pro-配对上又被断开) (`btmgmt bondable on` → `pair` → `trust` → imediatamente `connect`), ou use primeiro o controle web da versão nova (o kissqy diz que já foi mudado para SSH sempre conectado). Se quiser usar a função de "reparo" dele, compre o Nova 2 Lite que a acompanha.

**Se instalou um robotd modificado por você, não clique em "instalar / atualizar firmware" no console do kissqy**
Sintoma: esse botão substitui o robotd da placa. O suporte a IMU I²C que adicionamos ao robotd e o P / D / torque da versão ajustável local seriam sobrescritos (deduzido lendo o código, nunca cliquei de verdade).
Causa: ele reinstala o robotd que vem junto no pacote de instalação do kissqy; o script de instalação dele também apaga o `servo-test-parameters.json` (de propósito, para limpar os parâmetros manuais de versões antigas).
→ Quando o nosso console local está conectado à nossa placa de versão ajustável, ele bloqueia esse botão; conectando com o console original do kissqy, ou com o console antigo no cartão antigo (R17 mais o patch de IMU I²C), ninguém bloqueia, então não clique. Se de fato quiser voltar ao original, use o console original do kissqy para instalar e, depois de instalar, desenergize o servo uma vez (veja "P / D / limite de torque do servo ficam na RAM").

**No modo de calibração do fork, o Studio mostra sempre "programa principal iniciando"**
Sintoma: em 2026-10-20, cartão novo, o programa principal rodando em modo de calibração (`--commissioning`), servos e IMU sendo lidos, mas o Studio continuava escrevendo "programa principal iniciando", sem nenhuma leitura, e os dois primeiros passos da lista de início não podiam ser feitos.
Causa: o `robot.busStatus`, na fase de inicialização, responde o relatório de inicialização (`phase: configuring_bus`). No modo de movimento, ele é limpo depois da primeira leitura bem-sucedida, mas o modo de calibração nunca o limpa, então responde sempre `configuring_bus`, e o snapshot em tempo real (`ready`, `last_sample`) nunca foi entregue. No computador não se detectou porque o nosso programa principal falso foi escrito segundo o "comportamento imaginado", respondendo o snapshot assim que o modo de calibração sobe.
→ fork `341b68f`: no modo de calibração, também limpar depois da primeira leitura bem-sucedida. O sinal na versão antiga do fork é `phase` ficar sempre `configuring_bus` enquanto `total_success` cresce. O programa principal falso e os dados de teste devem ser escritos replicando exatamente o que foi gravado do robô real.

**Com o Clash ligado no computador (proxy do sistema), `http://duck-xxxx.local:8000` dá 502**
Sintoma: em 2026-10-21 o pato conectou ao Wi-Fi de casa; o navegador abrindo `duck-0de6.local:8000` dá 502, enquanto abrir pelo IP e por `duck-0de6:8000` funciona normalmente.
Causa: a lista de exceções do proxy do sistema do Clash é `localhost;127.*;192.168.*;10.*;172.16-31.*;<local>`. O `<local>` só cobre nomes sem ponto, e `.local` tem ponto, sendo tratado como domínio da internet e enviado ao proxy.
→ No Windows, use `http://duck-xxxx:8000/` sem `.local` (vai por LLMNR, que está na lista de exceções), ou use direto o IP; dispositivos Apple usam `.local`; para quem usa o modo TUN, defina a rede local como direta no software de proxy. O Studio e o manual já dão o endereço por dispositivo.

**Imagem feita por nós, SSH na porta 22 recusa conexão: nenhuma chave de host foi gerada**
Sintoma: em 2026-10-21, cartão de aceitação versão 2, o pato responde ao ping e a página web abre, mas o SSH na porta 22 recusa a conexão.
Causa: o `sshd-keygen` do Debian só roda na "primeira inicialização" (`ConditionFirstBoot`). Ao fazer a imagem, o `/etc/machine-id` foi esvaziado para arquivo vazio, o que o systemd não trata como primeira inicialização, as chaves não foram geradas, o `sshd -t` falha e o ssh não sobe.
→ Adicione um drop-in no `ssh.service` que, antes de cada início, rode `ssh-keygen -A` (sem mexer nas que já existem) e depois `sshd -t`. Ao fazer a imagem, não conte com a "primeira inicialização" para fazer coisas automaticamente; o que for preciso, escreva você mesmo no serviço.

**Os passos 1 e 2 da lista de início foram pulados, e depois de gravar no programa principal ainda está em modo de calibração**
Sintoma: em 2026-10-21, cartão novo, o zero dos servos já fora calibrado antes e a IMU não se queria recalibrar, os dois primeiros passos foram pulados, e depois de gravar o passo 3, o programa principal sobe e ainda não entra em modo de movimento.
Causa: o fork exige "direção da IMU em uso confirmada" para entrar em modo de movimento. Pulando o passo 2, a direção nunca foi confirmada.
→ Passo 3 do Studio: se o passo 2 foi marcado como concluído ou pulado e a direção não foi confirmada, grava com a montagem padrão e marca como confirmada (montagem oficial da plaquinha de barramento, padrão do fork para BNO085, módulo LSM6DSV16X com x para baixo e z para a frente). Se a montagem for diferente, calibre uma vez em pé e depois grave.

**No modo de calibração o pato não consegue ficar em pé, só gira um servo por vez e, ao terminar, tira a carga**
Sintoma: querendo primeiro calibrar a IMU em pé e depois gravar no programa principal, o "habilitar postura em pé" do Studio está cinza no modo de calibração, e só dá para primeiro gravar uma calibração de IMU com a montagem padrão, mudar para o modo de movimento e só então levantar.
Causa: o modo de calibração do fork só tem mover um servo (gira até a posição e tira a carga), voltar ao centro e registrar o zero, sem "segurar o corpo todo em pé".
→ O fork `f4bbe53` adicionou o `hold-home`: os 15 servos juntos giram em 3 segundos até o HOME e travam, com a IMU sendo lida normalmente e a parada de emergência normal. O "habilitar postura em pé" do Studio no modo de calibração chama isso diretamente. Não cuida do equilíbrio, é preciso segurar. Escrito em 10-21, ainda não testado no robô real.

**Ao ligar o cartão novo, o hotspot do pato leva cerca de 2 minutos para aparecer** (corrigido em 20261021b)
Sintoma: em 2026-10-21, depois de gravar e ligar pela primeira vez, o celular procurou por dois minutos até ver `Microduck-xxxx`.
Causa: a primeira inicialização em si precisa expandir a partição, definir o nome e reconhecer a IMU; o programa de configuração de rede ainda precisa primeiro confirmar "não conecta a nenhum Wi-Fi" por 45 segundos completos antes de abrir o hotspot. O cartão novo não tem nenhum Wi-Fi salvo, e esses 45 segundos são espera à toa.
→ A partir da 20261021b: se não há nenhum Wi-Fi salvo, o hotspot abre no instante em que detecta que não há rede; quando não consegue verificar os Wi-Fi salvos, espera os 45 segundos como antes. Na imagem antiga, espere um pouco mais.

## Treinamento da política e transferência para o robô real

**Para o programa de execução, prefira alterar um que já existe, não escreva um conjunto próprio**
Sintoma: no fim de setembro, para testar primeiro servos e IMU, foi escrito um executor em Python, que foi crescendo até virar executor de política; em 10-11 foi usado para rodar o modelo do kissqy e, depois de excluir ritmo, tensão, direção e parâmetros dos servos, ainda não andava, e as diferenças restantes estavam todas na camada de execução, sem como investigar.
Causa: a política é muito sensível ao lado de execução: o período de controle, o filtro de ação, se a velocidade da junta está atrasada um quadro, se IMU e servo são lidos no mesmo instante, tudo precisa ser igual ao do treinamento e ao do lado de execução do autor original. Escrever outro conjunto faz de cada detalhe uma variável invisível. O robotd oficial na época só suportava Dynamixel, e fizemos um fork dele em 9-18 para adaptar ao Feetech, travou em a IMU não estar ligada, e só então desviamos para escrever Python.
→ Se existe um lado de execução pronto que funciona (o robotd oficial, o R17 do kissqy), altere-o, completando o que falta (por exemplo, adicionar IMU I²C ao robotd). As pequenas ferramentas escritas por nós servem só para testar hardware (check-up dos servos, conferência de direção, movimento de uma junta), não para rodar a política.

**Ao testar o modelo de marcha, não segure o corpo com a mão**
Sintoma: em 2026-10-11, com o modelo walk do kissqy, com o corpo segurado na mão, dar 0 / 0,05 / 0,15 m/s só trocava a postura uma vez, e depois ficava parado por alguns segundos; colocado no chão sem apoio, em 0,4 segundo as duas pernas começavam a flexionar e estender alternadamente.
Causa: nesse tipo de modelo não há "batida de ritmo" na entrada; o passo vem do balanço do corpo e da transferência do centro de gravidade, e depois é conduzido pela IMU e pelo retorno das juntas. Com o corpo segurado, o corpo não balança, e a saída logo para numa postura estática.
→ Coloque no chão, com as duas mãos de cada lado como proteção simbólica a 2–3 cm, e pegue se cair. Velocidade 0 já é "parado em pé", não serve para julgar se vai andar.

**Quando ao andar todo o corpo tira a carga: primeiro veja se é proteção do executor, e não o modelo**
Sintoma: o pato mal começa a mexer as pernas e para, em seguida todos os servos tiram a carga juntos e o pato desaba.
Causa: o executor tem duas proteções definidas segundo pequenos movimentos de bancada. Uma é parar se a tensão de qualquer servo ficar abaixo de 6,6 V; ao andar a corrente é grande, e com alimentação de 7,4 V a tensão no lado do servo cai a 6,5 V e dispara; a outra é, depois de parar, manter no lugar, o que exige conferir que o desvio de posição seja ≤ 1°, e um pato que está se mexendo ou afundando sob P5 não consegue, então cai em "tudo sem carga".
→ Já alterado: nas fases de manter e recuperar, a tensão baixa não tira mais a carga, o critério de manter foi relaxado para 5°, e o retorno à postura em pé continua em 1°. A fonte foi ajustada para cerca de 8,0 V para dar margem (limite do HD-1910 é 8,4 V), e na 7ª rodada de 10 segundos a tensão mínima foi 7,6 V.

**Não aumente o ganho de uma vez em muito, a corrente derruba a fonte**
Sintoma: com P5 as pernas não acompanhavam o alvo (diferença de 6–7°), e ao mudar para P10, em 0,24 segundo a soma das leituras de corrente dos servos foi de cerca de 26 A, a tensão dos 14 servos caiu juntas para 5,4–5,8 V, e a proteção parou.
Causa: quanto maior o P, maior a força do servo para o mesmo erro, mais de uma dezena fazendo força juntos, e a fonte ajustável não aguenta. Além disso, o BAM do treinamento usa justamente P5, e aumentar o P já se afasta das condições de treinamento.
→ Se for aumentar, teste primeiro 6–8, observando a tensão; para movimentos grandes de verdade, use uma fonte que consiga entregar de uma vez mais de uma dezena de amperes, como bateria de lítio 2S.

**Assim que parte, a tensão desaba: acrescente partida suave ao movimento**
Sintoma: rodando exatamente como no treinamento (sem escala, sem filtro), em 0,3 segundo a tensão dos 14 servos caiu juntas para 4,6–5,2 V, e a proteção parou.
Causa: o primeiro quadro salta direto para a postura que o modelo quer, mais de uma dezena de servos fazendo força forte ao mesmo tempo, e o pico de corrente no momento da partida é o maior, que a fonte ajustável e os cabos de alimentação não acompanham.
→ O executor ganhou partida suave: no primeiro 1 segundo a amplitude do movimento sobe linearmente de 0 a 100% (padrão ligado na configuração do kissqy, alterável com `--ramp`). Depois de adicionada, com os mesmos parâmetros, completou 10 segundos, com mínimo de 7,5 V. A partida suave cuida só da partida; quando o movimento já está pleno, ainda pode derrubar a fonte ajustável, e a longo prazo é preciso trocar por bateria.

**O 0,9 / 0,5 / 0,7 do kissqy não são parâmetros de treinamento**
Sintoma: o pacote de implantação dele tem dois conjuntos de números: `deployment-profile.toml` diz escala 1,0, sem filtro; `deployment-execution.json` diz escala 0,9, filtro da cabeça 0,5, filtro das pernas 0,7.
Causa: o modelo foi treinado com 1 / 1 / 1; 0,9 / 0,5 / 0,7 são valores padrão que ele copiou do programa de execução oficial do pato (ajustado para Dynamixel), o robotd dele dá prioridade a este último e ainda multiplica extra pela compensação de tensão 7,4/V.
→ Teste os dois conjuntos: o executor usa por padrão os valores de execução dele, e com `--training-mapping` usa exatamente os do treinamento. A função de cada parâmetro está em [2026-10-11 teste no robô real do kissqy](docs/HD1910-20261011-kissqy-walk上机实测.md#3-运行参数每个是干什么的为什么有两套).

**Ao instalar o R17 ou mudar para modo de depuração, os servos primeiro tiram a carga e o pato desaba**
Sintoma: em 2026-10-12, ao instalar o R17, o pato que estava com carga de repente amoleceu; o robotd em modo de depuração (commissioning), a cada início, também tira a carga dos 15 servos.
Causa: o projeto dele é "tirar a carga ao ligar": o primeiro passo da instalação é fazer o serviço antigo tirar a carga, e o modo de depuração também tira a carga ao iniciar. O modo de movimento, ao iniciar, não tira a carga por conta própria.
→ Antes de instalar o R17, clicar em "mudar para modo de calibração" ou reiniciar o modo de depuração, segure o pato ou deixe-o deitado.

**Na confirmação da direção da IMU, não segure com a mão um pato mole: primeiro faça-o ir ao HOME e depois meça**
Sintoma: ao confirmar a direção de montagem da IMU, exige-se corpo vertical, com desvio da vertical de no máximo 5°. As pernas do pato sem carga estão moles, e segurando com a mão a primeira leitura foi 15,2°, sem passar.
Causa: a postura segurada com a mão já é torta (desta vez, cabeça baixa para a frente cerca de 13° e inclinado para a esquerda cerca de 8°), e o pato mole muda ao menor balanço.
→ Primeiro aplique carga e faça o pato ir ao HOME (a "postura em pé" do servo-web e o HOME oficial são o mesmo conjunto de ângulos); sozinho em pé leu 4,95°; depois incline o pato inteiro para a frente 15–30° e veja se a direção da variação é para a frente. Hoje o `verify-imu` do robotd só pode ser usado em modo de depuração, e o modo de depuração tira a carga ao iniciar, então em 2026-10-12 foi usada a leitura do servo-web, escrevendo manualmente com o mesmo critério; detalhes no [registro daquela noite](docs/HD1910-20261012-kissqy整套上机.md).
**Correção (noite de 2026-10-12)**: os 4,95° lidos naquela vez eram em grande parte o desvio da IMU montada torta, não a postura natural do pato. Depois de a direção estar certa ainda é preciso calibrar o zero, veja abaixo "IMU montada torta em 8,5°".

**Se outro programa aplicou carga e depois você trocou para o kissqy, o HOME é recusado**
Sintoma: o pato estava em pé com o servo-web; depois de mudar para o modo de movimento do R17 e enviar HOME, as 4 vezes reportaram `ID 20: temporary P/D readback mismatch; torque-on refused`.
Causa: o programa dele, ao ver que o servo já está com carga, assume que foi ele que aplicou antes, e só confere se P/D são os que ele quer, P5/D20, sem reescrever. A carga do servo-web usa P32/D40, e a conferência naturalmente não passa.
→ Primeiro tire a carga (`robot.relax`, segurando o pato) e depois HOME (`robot.init`). Ele escreve P5/D20, confirma por releitura, aplica carga e em 2 segundos gira até o HOME. Ao ir ao HOME o corpo deve estar a menos de 10° da vertical.

**IMU montada torta em 8,5°: assim que o modelo assume, dispara para trás**
Sintoma: na noite de 2026-10-12, depois de o modelo assumir, o mais rápido caía para trás em 0,6 segundo e o mais lento em 21 segundos, com o alvo das pernas saturado em ±90°～±100°; quanto mais inclinada para a frente a leitura do corpo antes de assumir, mais rápido o descontrole. Foram verificados eixos da IMU, giroscópio e sinais da velocidade das juntas, todos corretos.
Causa: no treinamento do modelo, o pato em pé no HOME, com os pés planos no chão, tem o corpo horizontal (o keyframe `STAND` do MJCF oficial, IMU lê 0°). O nosso módulo BNO085 foi montado torto, cerca de 8,5° para a frente e 1,75° para a direita: com o pato em pé reto, a IMU diz "inclinado 8,5° para a frente", e o modelo fica sempre corrigindo para trás. O comentário do código de treinamento oficial também diz que o desvio fixo de pitch da IMU do robô real deve ser corrigido em tempo de execução, e o treinamento não cuida disso.
→ Em pé no HOME, coloque na simulação os ângulos das juntas do robô real naquele instante, calcule quanto o corpo "deveria" estar inclinado e subtraia da leitura da IMU: essa é a diferença; incorpore-a ao quaternion de montagem da IMU (M′ = C ⊗ M). Passos e script em [`tools/radxa/onboard-analysis/`](tools/radxa/onboard-analysis/). Depois da calibração, o modelo assumiu por 70 segundos sem cair, com inclinação média de 0,2°, e ao empurrar o joystick começou a dar passos alternados. A investigação completa está no [registro do robô real da noite de 10-12](docs/HD1910-20261012-夜-IMU校准与首次迈步.md#4-一接管就猛冲怎么一步步找到-imu-偏差).

**A leitura da IMU deriva: depois de queda ou batida na IMU, reverifique o zero**
Sintoma: em pé no HOME, com ângulos das juntas quase iguais, a leitura de inclinação da IMU para a frente foi primeiro 5,2° e depois 8,6°.
Causa: o módulo da IMU foi mexido (no meio houve algumas quedas, e ainda mexeram no fio da IMU); a flexão das peças impressas sob esforço e a folga do disco do servo também dão uma ou duas graus de diferença.
→ Fixe o módulo firmemente (combinamos com o parceiro mudar para fixação com parafusos, e depois de fixar, recalibrar o zero uma vez). Depois de queda forte, batida na IMU ou troca de fio, reverifique conforme o item anterior, e se o desvio passar de 1°～2°, recalibre.

**Em pé no HOME os joelhos são empurrados para baixo, e o corpo realmente se inclina para a frente**
Sintoma: com o mesmo HOME, às vezes os dois joelhos chegam à posição, outras vezes são empurrados 5°～9° e o corpo se inclina até 17° para a frente, e o segundo toque de Start é recusado.
Causa: o HOME usa o ganho P5 do treinamento, que é mole, e o joelho recebe a maior carga; a maneira de descer para ficar em pé é diferente, e o ponto em que para também.
→ Coloque em piso plano, tire a mão, espere estabilizar e só então aperte o segundo toque. Não aumente o ganho por causa disso: afasta das condições de treinamento, e a corrente ainda derruba a fonte (veja acima "Não aumente o ganho de uma vez em muito").

**Power bank não aguenta os servos: quando a corrente é grande, recua para 5 V**
Sintoma: toda vez que volta ao HOME a partir da postura caída, a tensão cai a 5 V; não chega a ficar em pé, o segundo toque de Start é recusado, volta de novo ao HOME, em ciclo.
Causa: power bank PD de carga rápida com cabo de gatilho: em sobrecorrente a proteção do protocolo recua para 5 V. A 5 V, o torque e a velocidade do servo caem de três a quatro décimos; 5 V também é baixo até o limite inferior do step-down do HAT para a placa principal, e a placa principal pode reiniciar.
→ Use a bateria NP-F550, ou a fonte ajustável (8,0 V, limite de corrente no máximo). Os fios da fonte ajustável devem ser curtos e grossos: a 8 V a tensão no servo ainda cai para cerca de 7,0 V, e uma queda de 1 V nos fios é demais.

**A sola de TPU também varia em dureza: 95A é dura; com a sola muito escorregadia, o modelo vira passinhos miúdos (na simulação é assim, no robô real a verificar)**
Sintoma: da noite de 2026-10-12 a 10-13, o pato sobre a mesa, com o joystick empurrado, alterna as pernas, mas os passos são miúdos e avança pouco; o usuário achou que sobre um mousepad ficava melhor (sensação, sem dados).
Causa: o kissqy avisou que a sola precisa ser TPU, mas a nossa já era TPU, de **95A**, dura. O kissqy diz que o dele de 90A em dois dias endureceu e começou a escorregar, e então trocou por 85A. Este modelo foi treinado com o atrito da sola variando aleatoriamente só entre 0,7～1,3, sem nunca ter visto chão mais escorregadio; na simulação, alterando só o atrito, 0,5 quase não tem efeito, 0,3 vira passinhos de 4,5 Hz, quase só tremor de alta frequência, com o pé levantando só 7 mm, e com 0,2 não anda. Mas depois de mudar o D para 0, o robô real, sobre a mesma mesa, não tremeu mais, e a simulação não explica isso, então "escorregadio demais" é só uma suspeita não excluída. O atrito do robô real ainda não medimos.
→ Trocar para sola mais macia é barato e vale tentar: TPU 85A, ou placa de pé em PLA com folha antiderrapante de silicone / borracha de 1～2 mm colada (os dois pés com a mesma espessura, bem colada e cobrindo tudo, ponta do pé chanfrada, sem passar da placa do pé; na lista de peças do episódio 1 do vídeo de montagem do 机械行者Robo, no conjunto do pé há "placa do pé / almofada antiderrapante"); não use esponja grossa nem EVA. Para medir o atrito use um plano inclinado: coeficiente de atrito = tan(ângulo em que começa a deslizar), 35° ≈ 0,7 é o limite inferior do treinamento; o pato inteiro em cima primeiro tombaria, então use um bloco baixo do mesmo material. A verificação mais simples: com os mesmos parâmetros, na mesma mesa, ande uma série antes e outra depois de trocar a sola, comparando tremor e saída do chão. Detalhes em [registro de 10-14 de dia §6](docs/HD1910-20261014-白天-仿真找原因与新版放开参数.md#6-脚底摩擦和鞋底).

**Antes de comparar simulação com o robô real, alinhe as condições: escala de ação, filtro, peso, velocidade**
Sintoma: na manhã de 2026-10-14, comparando simulação com o robô real, o joelho de apoio na simulação esticava e o pé levantava 12 mm, e no robô real não esticava e levantava só 5 mm, e então se passou a suspeitar dos parâmetros do servo, do peso e da sola.
Causa: as condições da simulação e do robô real eram diferentes, e de manhã não foram alinhadas. No robô real, no cartão antigo, a escala de ação efetiva do modelo conjunto é cerca de 0,83 (0,9 × compensação de tensão 7,4 / tensão), filtro das pernas 0,7 e da cabeça 0,5, e na simulação eram 1,0 e sem filtro; o modelo que o kissqy usou no treinamento é de 820 g (soma das massas dos componentes no `deployment-contract.json` do pacote do modelo), e o modelo oficial que usamos na simulação é de 737 g. Depois de alinhar, a simulação ainda apresenta tremor de alta frequência que o robô real não tem, e a causa não foi investigada, então os números da simulação servem só como direção. Detalhes em [registro de 10-14 de dia §1, §2](docs/HD1910-20261014-白天-仿真找原因与新版放开参数.md#1-仿真怎么做的跟真机差在哪).

**A escala e o filtro do modelo conjunto não estão no `robotd.toml`; alterar o toml não adianta**
Sintoma: em 2026-10-13, alteramos no `robotd.toml` o `action_scale` (1,0, 0,8) e o filtro de cabeça e pernas e fizemos vários grupos de comparação, e todas as conclusões foram depois anuladas.

**Arrastar o pé no chão: primeiro calcule qual pé e qual parte está baixa; não corra para calibrar o zero nem para ajustar separadamente as pernas esquerda e direita**
Sintoma: em 2026-10-14 o pato arrastava os pés ao andar, mais evidente no pé esquerdo. De início achou-se que o corpo pendia para a esquerda, que a IMU estava imprecisa ou que o zero estava impreciso, e quis-se ajustar as pernas esquerda e direita separadamente.
Causa: calculando a folga do chão depois de endireitar o corpo pela IMU (`tools/gait-analysis/foot_clear.py`), **os dois pés levantavam apenas metade do da simulação** (3～6 mm contra 11～12 mm): no apoio o modelo quer o joelho esticado, e no robô real ficou sempre dobrado (os parâmetros do servo são do mesmo 1910, a diferença está em condições como P, limite de torque e peso, ainda em separação). O pé esquerdo parece arrastar mais porque, ao dar o passo, a ponta dele aponta para baixo (o direito e a simulação têm o calcanhar mais baixo), e quando a perna direita apoia o corpo cai 1,5° mais para a frente; esses dois pontos só aparecem depois de mudar o D para 0. O roll da IMU foi compensado; o zero das juntas é igual à esquerda e à direita na direção frente-trás, e na direção lateral os dois pés calculados diferem cerca de 1,6°～2,6°, ainda não investigado.
→ Primeiro, com o script, calcule direito "qual pé, ponta ou calcanhar, qual junta, como o corpo se move" e só então mexa nos parâmetros. Para o que tem relação com o D, primeiro teste outro conjunto de D; para o que a leitura do servo não mostra (o pé não está plano, folga mecânica), investigue com câmera lenta de lado e com a mão. Atenção: um zero da IMU desviado em 1° faz, nos cálculos, os dois pés diferirem cerca de 2 mm; calibre primeiro a IMU antes de comparar esquerda e direita. Detalhes em [registro do robô real da noite de 10-13 §7](docs/HD1910-20261013-夜-掉电-舵机D与蹭地.md#7-蹭地两只脚都只抬了仿真的一半).
**Acréscimo (10-14 de dia)**: depois de a simulação alinhar a escala de ação do robô real (cerca de 0,83), o filtro de cabeça e pernas e o peso de treinamento do kissqy (820 g), o joelho de apoio ficou próximo do robô real, e o "joelho não estica" visto na simulação em grande parte se explica por essas condições (veja acima "Antes de comparar simulação com o robô real, alinhe as condições"); na simulação, subir a escala de 0,83 para 1,0 levanta cerca de 3 mm a mais, e no robô real mudar a escala conjunta para 1,0, multiplicada pela compensação de tensão, aumenta só 11% (na simulação é 20%), e por estimativa linear o efeito é de cerca de metade do da simulação, ainda assim vale tentar. A não coplanaridade dos dois pés na direção lateral também foi investigada: os dois rolls do quadril abrem para fora, diferente a cada vez, parecendo ser empurrados pelo peso (suposição; veja "Servos / calibração"). Detalhes em [registro de 10-14 de dia](docs/HD1910-20261014-白天-仿真找原因与新版放开参数.md).

**A atitude calculada pelo próprio BNO085 ao andar dá saltos: a causa raiz de "cai depois de dois ou três passos"**
Sintoma: de 2026-10-12 a 10-14, depois de o modelo assumir ficava estável em pé, mas ao empurrar o joystick dava dois ou três passos e caía de frente; trocar a sola, ajustar o D do servo, ajustar filtro e escala, nada adiantou. Quanto mais o pé agarra o chão (fita adesiva → silicone) e quanto mais duro o servo, mais rápido cai.
Causa: a atitude fundida pelo próprio chip BNO085 (vetor de rotação de jogo) ao andar (o início do surto fica cerca de metade antes e depois do apoio do pé) salta 20～60° em 20 ms, enquanto no mesmo instante o giroscópio do chip girou só 1～2°. A direção da gravidade que o modelo vê salta junto, e ele pensa que está caindo, e ao corrigir realmente cai. Nos quadros de andar empurrando o joystick, os saltos ocupam de 1,9% (fita adesiva) a 23～32% (silicone, P5); depois da partida, a mediana do primeiro surto é 1,8 s, exatamente os "dois ou três passos"; cerca de oito décimos das quedas ao andar têm salto nos 1,5 s antes da queda (sem linha de base, só como referência). O giroscópio em si é confiável: correlação de 0,97～0,99 com a velocidade angular derivada do quaternion, e a cinemática direta das pernas também fica do lado do giroscópio. O comprimento dos valores brutos do quaternion é normal, não é erro de leitura do I²C. Por que o chip salta por dentro, não conseguimos ver; suposição: o impacto do apoio do pé atrapalha a correção do acelerômetro.
→ Não confie na atitude do chip; integre você mesmo o giroscópio do chip: `[trunk_imu] bno08x_fusion = "gyro"` no robotd (no nosso fork, branch [`hd1910-v167-gyro-fusion`](https://github.com/fanhao375/Microduck-kissqy/tree/hd1910-v167-gyro-fusion), o padrão continua `chip`, é preciso trocar você mesmo; o jeito de trocar está em IMU-MODULE.md 4.4 lá, **não adicione chaves à mão com nano ou sed**). Teste real da noite de 10-15: no modo chip, empurrando o joystick, 9 s e caiu 2 vezes; no modo gyro, empurrando o joystick por 60 s sem cair nenhuma, ficou mais de 10 minutos em modo walk (60 s empurrando o joystick) e caiu só 1 vez, o chip ainda saltou 745 vezes e a via do modelo não saltou junto. Não foi feita comparação alternada completa; o usuário viu no local e decidiu usar direto o gyro. O processo completo está no [registro de 10-15](docs/HD1910-20261015-IMU乱跳根因与陀螺融合上机.md).

**Três dias ajustando parâmetros valem menos que primeiro checar se os próprios dados batem; compare as diferenças uma a uma com quem fez funcionar**
Sintoma: de 10-12 a 10-14 ajustamos sola, D do servo, filtro, escala, comparando com a simulação, e toda vez era "parece um pouco melhor, ou talvez não", e por um tempo se preparou retreinar o modelo.
Causa: o problema não estava nesses parâmetros. No grupo alguém, com os mesmos servos, o mesmo modelo do kissqy, "P5 D0, o resto tudo padrão", fez funcionar, o que mostra que servos e modelo em si não têm problema, e o problema está nas diferenças entre nós e ele (chip da IMU, alimentação, peso, sola, mecânica). O verdadeiro indício foi um fenômeno "fisicamente impossível": o giroscópio dizia que quase não girou, e a atitude saltou dezenas de graus.
→ Primeiro liste as diferenças em relação a quem fez funcionar e descarte uma a uma (peso 806 g contra 820 g do treinamento, descartado; parâmetros iguais aos dele, caiu do mesmo jeito; a IMU sobra como maior suspeita). Depois, com uma verificação de autoconsistência do tipo "gravidade do quadro anterior + giroscópio deste quadro extrapolado por 20 ms, diferindo mais de 5° da gravidade deste quadro", ache o sensor que está mentindo. O algoritmo novo roda primeiro em sombra (só acompanha, não publica), e só depois de os dados do robô real confirmarem que está tudo bem é que se troca. Critério e scripts de estatística por segmento: `judge_block.py` e `ab_blocks.py` em [`tools/radxa/onboard-analysis/`](tools/radxa/onboard-analysis/).

**A régua para julgar saltos também engana: o giroscópio da gravação passou por mediana de três pontos, um quadro atrás da atitude**
Sintoma: no segmento chip em sombra da noite de 10-15, a via de fusão do giroscópio teve 5 ocorrências de "saltou mais de 5°" pelo critério original, 4 delas nos 0,5 s antes de uma queda e 1 logo após parar de empurrar, com o corpo balançando forte. Simulando a via de publicação do modo gyro, deu 0 vezes, mas o máximo foi 3,75°, com margem de só 1,25°, e a regra original "uma ocorrência volta ao chip" poderia ser disparada a qualquer momento pela própria queda.
Causa: o `imu.gyro` da gravação passou por mediana de três pontos, ficando um quadro atrás do real; o `imu.fusion.fused` não passou pela mediana. Extrapolar com a velocidade angular atrasada um quadro, quando o corpo gira 130～640° por segundo, dá uma diferença de 5°. Esses 5 quadros de fusão estavam todos em "rejeitar" o chip (só integração do giroscópio, impossível dar salto de passo inteiro), e o ângulo de rotação do quaternion fundido entre dois quadros bate com a integração do giroscópio bruto de 100 Hz (dentro do alinhamento de um relatório). Mudando a extrapolação para usar o giroscópio do quadro seguinte, deu 0 vezes.
→ A velocidade angular da extrapolação deve estar alinhada com o atraso da atitude: a via que o modelo vê (`safety.gravity`, que também passou pela mediana) combina com o giroscópio do mesmo quadro, e o valor bruto da fusão combina com o giroscópio do quadro seguinte. A regra de parada é dividida pelo julgamento da fusão: se em ±2 quadros ao redor do salto houver `realign_long`, `realign_gap`, `fallback`, `follow`, uma ocorrência já volta; para os que são só aceitar, rejeitar e perseguir com limite de velocidade, não contam os que estão no 1 s antes da queda ou com inclinação do quadro anterior ≥30°, e nos demais, cada segmento com ≥3 ocorrências volta. Uma travada na leitura da IMU (alguns quadros sem atualizar, um quadro alcançando de uma vez ao se recuperar) também conta como degrau suave, e é preciso olhar um por um. Veja [registro de 10-15 §5.5](docs/HD1910-20261015-IMU乱跳根因与陀螺融合上机.md#55-停止规则判跳变的尺子在摔倒时会误报).

**Depois de consertada a IMU, a direção é fraca: as juntas só acompanham metade do alvo** (ainda não resolvido)
Sintoma: na noite de 10-15, depois de o modo gyro andar de forma estável, direção pelo joystick direito: girando no lugar só cerca de um quarto do comando (58°/s e gira só 15°/s), e girando enquanto anda praticamente não gira (61～79°/s e gira só −4～11°/s, uma vez girou ao contrário).
Causa: comparando alvo do modelo e servo real: guinada do quadril acompanha 57～95%, roll do quadril 31～56%, joelho 48～55%, pitch do quadril 45～67%. As pernas só balançam metade, o pé não levanta, e não dá para girar o pé no ar; com a sola toda de silicone colada ao chão também não consegue torcer (suposição). A direção só foi testada no modo gyro; pelo código, a velocidade angular usada na direção é o valor bruto do giroscópio do chip nos dois modos, então se infere que não tem relação com a alteração da IMU; infere-se também que é aquilo que antes se dizia, "o joelho só balança metade", antes encoberto pelos saltos da IMU.
→ Mude uma coisa de cada vez: primeiro pergunte a quem fez funcionar se a direção responde bem e de que material é a sola; depois teste escala de ação 0,9 → 1,0; depois P do servo 5 → 6, 7; troque pela fonte de 10 A e compare de novo. Cada vez meça com o mesmo método: girar para a esquerda e para a direita no lugar por 3 segundos cada, girar enquanto anda algumas vezes, comparando velocidade de giro real e proporção de acompanhamento das juntas.

## Ferramentas

**STM32G0 virgem: depois da primeira gravação o programa não roda e fica parado no Bootloader embutido da ST**
Sintoma: a gravação pelo CubeProgrammer e a verificação por releitura passam, mas depois do reset o programa não dá sinal: a RAM ainda tem valores aleatórios de energização, e parando a CPU vê-se PC = `0x1FFF…` (o Bootloader da memória do sistema, os registradores R6/R7 são USART1/I²C1, varrendo interfaces esperando alguém gravar). Causa: o G0, ao ligar, verifica se a primeira palavra da Flash está vazia, e o resultado fica em `FLASH_ACR.EMPTY`, que **só é atualizado na energização (carga dos bytes de opção)**; em chip virgem, ao ligar EMPTY=1, e o reset por software depois de gravar não verifica de novo, e o chip ainda acha que está vazio.
→ **Em chip virgem, depois da primeira gravação, desligue e ligue a energia uma vez**. Apertar o reset (NRST) também não verifica de novo, não adianta. Depois, ao gravar de novo (Flash não vazia), não há esse problema (2026-09-22, primeira placa do imu_to_dxl).

**O conector de 20 pinos do ST-LINK/V2 não é igual em todos os fabricantes, e o GND só vale nos pinos 12/18/20**
Na definição oficial da ST, os pinos 4/6/8/10 também são GND, mas em algumas versões (por exemplo, a que tem UART/SWIM) os pinos 4/6/8/10/14 do lado do depurador são UART-RX, UART-TX, BOOT0, SWIM, SWIM-RST. Ligar o GND ao pino 4 pela tabela oficial equivale a ligar o terra da placa-alvo à serial do depurador. Além disso, **o pino 1 TVCC só mede tensão, não alimenta**; em algumas versões **o pino 19 VDD fornece 3,3 V para fora**.
→ O SWD usa só quatro fios: **1 TVCC, 7 SWDIO, 9 SWCLK, 20 GND**; quando a placa se alimenta sozinha pelo barramento, não ligue o pino 19, e não ponha duas fontes em paralelo. Se depois de ligar o ST-Link cai repetidamente (no gerenciador de dispositivos, "falha na solicitação do descritor de dispositivo"), na maioria das vezes a ligação derrubou a alimentação dele: primeiro ligue o ST-Link sozinho para confirmar que está bom e depois ligue a placa.

**O Keil é velho demais para compilar projetos CMSIS 6: `cmsis_clang.h` não é encontrado**
O MDK 5.24 traz o Arm Compiler 6.7; o `cmsis_compiler.h` do CMSIS 6 exige `__ARMCC_VERSION >= 6100100` (6.10.1), e com versão insuficiente ele trata como clang comum e procura um `cmsis_clang.h` que simplesmente não existe.
→ Instale o MDK 5.4x (o 5.41 traz o 6.22; sem licença é a versão Lite com limite de 32 KB, e este firmware de 10 KB cabe). O pacote de dispositivo `Keil.STM32G0xx_DFP` também precisa ser instalado por você nas versões antigas do Keil.

**Na URT-2, alimentar o servo primeiro e conectar o USB depois deixa o barramento sem comunicação**
Sintoma: os 15 não respondem, e só o ping broadcast recebe alguns bytes todos 0; medindo o barramento S–G com o multímetro em repouso há só 2,1 V (o normal é cerca de 4,5 V); sem o USB conectado, a barra de pinos de 5 V da placa tem inexplicavelmente 2,1 V. Com a placa sem servo, em vazio, S–G volta a ser os 4,5 V normais. A causa é que a lógica da placa só recebe energia do USB, o lado do servo puxa o barramento a 5 V primeiro, com a placa ainda sem energia, e a corrente reflui do pino S para o trilho de 5 V da placa; quando o USB é conectado depois, a parte de conversão de nível já está presa num estado meio morto, que prende o barramento em 2,1 V.
→ **Ordem: primeiro conecte o USB, depois alimente os servos**. Se já foi ao contrário, desconecte os dois lados e recomece. Não corra a suspeitar de S/G invertidos ou placa com defeito (em 2026-09-17 perdemos uma hora nisso).

**A extensão Markdown Editor do VS Code não mostra imagens em HTML**
O README usa cartões de duas colunas montados com `<table><img>`, e essa extensão não interpreta caminhos relativos em HTML puro, deixando as imagens vazias. No GitHub fica bom.
→ Use a pré-visualização embutida do VS Code (`Ctrl+Shift+V`).

**No Windows, `core.autocrlf=true` destrói arquivos binários**
O cabeçalho dos PDFs é em geral ASCII, o git os detecta automaticamente como texto por engano e faz a conversão LF→CRLF no checkout, e o arquivo fica diretamente corrompido.
→ No `.gitattributes`, declare `binary` para `*.pdf *.stl *.step *.png` e assim por diante.

**Ao publicar um Release no GitHub, passar um hash curto em `--target` falha; não use chinês no nome do anexo**
Sintoma: em 2026-10-20, `gh release create … --target 36854c7` reportou `Release.target_commitish is invalid`; anexos com nome em chinês têm o nome alterado depois do upload.
Causa: a API só aceita o hash completo de 40 dígitos ou o nome do branch; o nome do anexo só mantém ASCII.
→ `--target $(git rev-parse HEAD)`; para anexos use nome em inglês (`microduck-replica-日期-licenses.txt`), e a explicação em chinês escreva no corpo da página do release.

**Colocar uma tabela Markdown dentro do cartão de duas colunas da página inicial estraga a coluna inteira**
Sintoma: em 2026-10-20, foi adicionada ao cartão elétrico do README uma tabela de comparação de placas e, depois do push, as duas colunas de mecânica e algoritmo sumiram.
Causa: o cartão é montado com `<table><td>`, e ao colocar uma tabela Markdown dentro, na renderização do GitHub a tabela aninhada bagunçou a externa.
→ Dentro do cartão use só listas; antes de alterar a página inicial, renderize com `gh api markdown`, confira com uma captura de tela no navegador e só então faça o push.

**No Windows, ao alterar texto com Python, as quebras de linha viram CRLF silenciosamente**
Sintoma: em 2026-10-12, no Windows, usando `Path.write_text` do Python para alterar 3 linhas de comentário no `voice-setup.py` do branch do kissqy, depois do commit o `git diff --stat` mostrou o arquivo inteiro, mais de 150 linhas, todo alterado.
Causa: o `write_text` no Windows escreve por padrão `\n` como `\r\n`; o `.gitattributes` daquele repositório é `-text`, o git não faz conversão de quebra de linha, e o CRLF entrou no commit como estava. Em repositórios com `core.autocrlf=true`, no commit é convertido de volta para LF, e não se percebe, mas o arquivo da área de trabalho já mudou.
→ Ao alterar arquivos com Python, escreva `open(p, 'w', newline='')`, ou leia e escreva em bytes; antes do commit, veja se as linhas do `git diff --stat` batem com o que realmente foi alterado, e `file nome-do-arquivo` mostra se é CRLF. Aquele caso já foi revertido para LF com o commit `d1dcfa6`.
